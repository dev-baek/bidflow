# [Issue #19] Outbox 조회 간격의 로컬 대조 실험

- 상태: 사양 승인(#266), [DEBUG 계측·수집 연결 구현](../reports/issue-019-outbox-delay-implementation.md), [A1/B/A2 로컬 실측](../reports/issue-019-outbox-delay-aba.md) 완료. 100ms 후보만 기본 화면 P95 2초 기준을 통과했으나 기본 간격은 변경하지 않았다.
- 기존 이슈: [#19 부하·장애 검증](https://github.com/dev-baek/bidflow/issues/19), 관측성 연관: [#18](https://github.com/dev-baek/bidflow/issues/18).
- 근거: [입찰 20건과 Outbox 실측](../reports/issue-019-outbox-timing-evidence.md). 기본 화면 P95 2,936.95ms, 명령/결과 DB age P95 912ms/1,003ms였다.
- 유지할 계약: [브라우저 결과 관측](issue-019-browser-result-latency.md), [Outbox 구간 계측](issue-019-outbox-timing.md).

## S. 가설과 화면 범위

**가설:** 동일한 로컬 순차 입찰에서 Outbox fixed delay를 1,000ms에서 100ms로 줄이면 명령·결과의 INSERT→조회 age와 화면 관측 지연이 낮아진다. 반대로 이벤트가 없어도 미발행 SELECT를 더 자주 실행하므로 조회 빈도와 DB 비용이 늘 수 있다.

앱 화면·입찰 규칙·인증·WebSocket 계약은 바꾸지 않는다. 기존 두 사용자·20건 순차 E2E를 그대로 사용한다. 기본 관측과 25ms 보조 관측을 계속 동시에 기록하며, 보조 관측을 2초 기준 판정에 대신 사용하지 않는다. 100ms는 **실험 후보값**이지 채택한 기본값이 아니다.

## D. DB와 증적

DB migration·새 인덱스·데이터 정리·통계 reset은 없다. 기존 `enqueued_at`과 읽기 전용 SQL을 재사용한다. 업무 Clock(2030년)과 실제 성능 시계는 계속 분리한다.

회차별로 아래를 보존한다.

- 기준 commit, 순서/라벨, 실제 실행 인자, Java/Node/Chromium 버전, 서비스·컨테이너 식별 정보, 실행 시작/끝, 관측 창 길이.
- 브라우저 원본 20건과 기본/보조/개인 frame/HTTP의 P50·P95·P99, 미완료 수, 기본 2초 판정.
- 해당 경매의 requestId→Outbox eventId 연결과 허용 필드 로그. 명령/결과의 age·batchWait·sendAck 분포, 유효/누락/무효/중복/실패 수.
- 요청·승인 원장·서로 다른 원장 requestId·결과 이벤트 수, version 순 가격 역행, 최종 현재가·승자 일치 여부.
- 유휴/입찰 관측 창별 poll 완료 수·성공/실패·빈 poll 수·총 발행 수·관측 초당 완료 수. PostgreSQL 컨테이너 CPU 원본 표본과 표본 수·중앙값·최댓값.

원본 payload·Token·사용자 ID·자동입찰 최대가·이미지 URL·예외 원문·전체 로그·trace는 증적에 복사하지 않는다. 순차 E2E에 필요한 제출 금액은 기존 브라우저 증적 계약대로 남긴다. 새 경매의 데이터는 삭제하지 않는다.

## B. 최소 계측 보완

### 기존 동작 보존

`OutboxScheduler`의 `${bidflow.outbox.fixed-delay-ms:1000}`를 재사용한다. 새 설정 키를 만들지 않는다. fixed delay는 **이전 실행 종료 후 다음 실행까지의 간격**이다. 실행 시간·스케줄링 지연이 추가되므로 100ms를 정확히 초당 10회 실행하거나 이벤트 지연 상한 100ms로 설명하지 않는다.

`OutboxPublisher.publishPending`은 이미 성공 발행 수를 반환한다. 미발행 조회 조건·배치 limit 100·정렬·직렬 발행·Kafka Envelope·멱등 처리·트랜잭션·`published_at` 의미를 그대로 유지한다. 조회·발행 예외도 기존대로 Scheduler 호출자에게 전파한다.

### 조회 빈도를 확인할 opt-in DEBUG 로그

현재 이벤트별 로그는 빈 조회를 보여주지 않는다. 전체 SQL 로깅이나 새 모니터링 서비스를 도입하지 않고, `OutboxScheduler`에 DEBUG가 활성화된 경우만 호출당 완료 로그 하나를 남긴다.

| 필드 | 계약 |
|---|---|
| `event` | `outbox.poll.completed` |
| `outcome` | `SUCCEEDED` 또는 `FAILED` |
| `publishedCount` | 성공 반환 시 실제 반환값. 0이면 성공한 빈 poll. 실패 시 생략 |
| `durationMs` | 호출 직전→종료/예외까지 주입 가능한 단조 ticker. 역행/무효면 생략 |

업무 식별자·payload·예외 원문을 추가하지 않는다. 실패한 poll에서 일부 발행이 끝났을 수 있으므로 `publishedCount=0`을 만들어 넣지 않는다. 이 경우 회차의 조회/빈 조회·발행 집계는 정상 회차와 합치지 않는다. 로그/MDC 정리는 성공·실패 모두 보장하고, 로그 처리 오류가 정상 발행 결과나 원래 예외를 바꾸지 않게 한다.

기본 INFO 레벨에서는 이 로그를 내보내지 않는다. DEBUG가 꺼져 있으면 추가 타이밍/필드 구성도 건너뛴다. 이 로그는 발행 이벤트 성공 로그를 대체하지 않는다. 외부 endpoint·Metric Tag·새 의존성은 추가하지 않는다.

현재 코드에서 Scheduler 호출당 `findPending()`은 한 번이다. 따라서 **관측된 완료 호출 수는 미발행 조회 시도를 거친 호출 수**이지 PostgreSQL 전체 SELECT 수나 성공한 SQL 수가 아니다. 실패·관측 창 경계의 실행 중 호출·로그 누락은 별도 한계다. 코드 경로가 바뀌면 이 등식부터 다시 검증한다.

## I. A1→B→A2 실행 절차

| 순서 | 라벨 | fixed delay | 측정 |
|---|---|---:|---|
| 1 | A1 | 1,000ms | 유휴 60초 + 새 경매 20건 |
| 2 | B | 100ms | 유휴 60초 + 새 경매 20건 |
| 3 | A2 | 1,000ms | 유휴 60초 + 새 경매 20건 |

1. 같은 commit·Docker·Vite·Chromium을 사용하고 API 프로세스 하나만 실행한다. 별도 k6·기능 E2E·수동 입찰·Clock 변경을 겹치지 않는다. 다른 사용자 서비스/컨테이너를 임의로 중단하지 않는다.
2. 각 조건은 API 재시작으로 적용한다. `local,e2e`, localhost 바인딩과 동일한 Scheduler DEBUG 로그를 세 조건 모두 사용한다. 준비 완료 후 조건별로 기존 순차 20건을 한 번 워밍업한다. 워밍업 경매·결과도 식별해서 남기되 본측정 백분위에 합치지 않는다. 느린 첫 본측정 표본은 제외하지 않는다.
3. 대기 Outbox가 비워진 것을 확인한 뒤 유휴 60초 창을 관측한다. 의도적인 입찰/등록 없이 poll 빈도·빈 poll·DB CPU를 기록한다. 예상 외 발행이 있으면 숨기지 않고 오염된 유휴 창으로 표시한다. 측정 중 과거 이벤트를 삭제해 빈 상태를 만들지 않는다.
4. 새 경매를 준비하고 기존 지연 E2E를 worker 1개로 실행한다. runner는 20건의 첫 클릭 직전과 마지막 결과 완료/실패 종료에 명시적인 창 표시를 전달한다. 수집기는 **표시를 수신한 시각**으로 창을 열고 닫으며, 같은 수집기 프로세스의 단조 시계로 창 길이와 로그/CPU 수신 시각을 기록한다. 따라서 이 보조 창에는 프로세스 간 전달 오차가 있다. E2E의 요청별 지연은 기존 runner 시계 안에서만 계산하며 보조 창 시각과 빼지 않는다.
5. poll 로그는 해당 창 안에 수집기가 **수신한 완료 로그**를 센다. 이것은 DB에서 정확히 그 시간에 시작한 SELECT 수가 아니다. 비동기 로그 전달·창 양끝의 실행 중 호출에 영향받는다. 창 밖 완료 로그는 지연 표본에 끼워 넣지 않으며 경계 누락 가능성을 보고한다. 수집 지연/누락이 확인되면 빈도 비교는 미확인으로 둔다.
6. 동일 창에 PostgreSQL 컨테이너 하나의 `docker stats` CPU를 같은 주기로 수집한다. 각 표본의 수집기 상대 시각을 보존하고 유휴/입찰 창을 섞지 않는다. 창별 CPU 표본이 5개 미만이면 CPU 비교는 불충분으로 표시한다. Docker CPU는 호스트 전체 CPU나 SQL별 비용이 아니며, 부수적인 DB 작업도 포함한다. 메모리 사용량을 쿼리 비용이라고 해석하지 않는다.
7. 회차 직후 해당 경매만 SQL로 연결·무결성을 확인한다. A1/B/A2는 각각 새 경매이며 requestId로 짝지어진 실험이 아니다. 각 회차 지표를 따로 보고하고 60건을 한 분포로 합쳐 기준을 판정하지 않는다.
8. 종료·실패 모두 승인 전 기본 동작인 `local`/1,000ms로 복원하고 DEBUG를 끈다. 실제 활성 프로필·간격 설정과 health를 확인한다. 기존 사용자 프로세스/파일·볼륨은 보존한다.

API 실행 예시(다른 API가 같은 포트를 점유하지 않은 경우, 저장소 루트):

```sh
SPRING_PROFILES_ACTIVE=local,e2e SERVER_ADDRESS=127.0.0.1 \
  ./backend/gradlew -p backend :runtime:bootRun \
  --args='--bidflow.outbox.fixed-delay-ms=100 --logging.level.com.bidflow.runtime.OutboxScheduler=DEBUG'
```

A1/A2는 위 인자의 간격만 `1000`으로 바꾼다. 실제 워밍업·지연 E2E 명령은 [기존 재현 방법](../reports/issue-019-outbox-timing-evidence.md#재현과-검증)을 따른다. 위 명령만으로 창 표시·CPU 수집까지 수행된 것으로 간주하지 않는다. 해당 수집 연결은 사양 승인 후 구현·검증한다.

## T. TDD와 판정

구현 전 실패 테스트를 만들고 아래 경계를 검증한다.

- Scheduler는 성공/빈 반환값과 실패를 구분하고 기존 발행 호출을 한 번만 수행한다. 예외·publishedAt 인자 전달과 1,000ms 기본 설정 계약을 보존한다.
- 가짜 ticker로 duration·역행 시 숫자 생략을 검증한다. DEBUG off의 무관측, 실패 시 count 생략, 민감 필드 미기록, MDC 정리, 관측 실패 시 원래 결과/예외 유지도 확인한다.
- 창 경계·순서 오류·단조 시계 역행·poll 실패·필드 누락/잘못된 숫자를 성공 집계로 바꾸지 않는다. 같은 원본 파일/행을 두 번 투입하는 중복 입력도 거부한다. 빈 창은 0ms 지연이나 성공한 성능 실험이 아니다. 식별자가 없는 poll 로그의 전달 중복이나 원본에 없는 로그 누락까지 자동 검출했다고 주장하지 않는다.
- nearest-rank 백분위와 기존 E2E/Outbox 집계 함수를 재사용한다. CPU의 `%` 파싱·비정상 값·창 외 표본·최소 표본 수를 작은 fixture로 검증한다.

각 회차는 완료 20·미완료 0, 요청/승인 원장/서로 다른 원장 requestId/승인 결과 각 20, 가격 역행 0, 최종 30,000원·승자 일치, 명령/결과 각각 20개의 정상 계측 연결을 먼저 확인한다. 실패·누락이 있으면 원본은 남기되 유효한 성능 비교로 채택하지 않는다. 기본 P95 2초 초과만으로 SQL/로그 수집을 생략하지 않는다.

후보 B의 기본 화면 P95가 2초 이하인지 기존 임계값으로 판정한다. B의 기본 화면 P95·명령/결과 age P95가 A1과 A2 각각보다 모두 낮은지도 별도로 보고한다. A1/A2 차이가 크거나 B만 유리하지 않으면 실행 순서/환경 영향을 배제하지 못한 결과로 둔다. 재실행은 기존 실패를 지우지 않고 새 회차로 남긴다.

조회 빈도·빈 조회 비율·DB CPU 변화는 지연과 함께 보고한다. CPU 미수집·오염이 있으면 비용 절충은 미확인이다. 이 실험은 단일 로컬 A-B-A 확인이며 통계적 유의성·동시 부하·장애 안전성·운영 SLO 증명이 아니다. 성공하더라도 **기본 간격은 이 작업에서 변경하지 않는다.** 채택하려면 실측 보고 검토와 별도 설정 변경 PR이 필요하다. #19/#18도 자동으로 닫지 않는다.

AWS 접근·리소스 생성·과금 작업은 하지 않는다. 이번 문서 승인으로 AWS 사용이 승인되는 것은 아니다.
