# [Issue #416] Redis 복구 전후 입찰 상태 일치

- 상태: 검토 요청. 구현·데이터 전환은 별도 PR에서 검증한다.
- 추적: [#416](https://github.com/dev-baek/bidflow/issues/416), [Redis 복구 ADR](issue-026-redis-recovery-adr.md), [기존 복구 보고서](../reports/issue-086-redis-auction-recovery.md).

현재 직접 입찰이 승인되면 Redis는 새 선두의 유효 상한(`winnerMax`)을 직접 입찰가로 바꾼다. 그러나 PostgreSQL에서 복구할 때는 같은 사용자의 과거 자동입찰 상한이 있으면 그 값을 먼저 사용한다. 과거 상한이 작으면 이후 가격이 내려갈 수 있고, 크면 복구 전에는 없던 자동 응찰 여력이 되살아날 수 있다. **복구는 같은 확정 이력에 대해 Redis를 잃지 않은 경우와 동일한 다음 입찰 결과를 내야 한다.**

## D. 유효 상한의 원본과 기존 데이터 전환

- 경매의 유효 상한은 **가장 최근에 확정된 입찰 계산이 반환한 현재 선두의 상한**이다. 사용자별 자동입찰 설정과는 별개다. 최종 원본은 PostgreSQL 경매 행이며 Redis는 파생 상태다.
- 새 비공개 컬럼에 유효 상한을 저장한다. 승인 정산에서 가격·선두·마감·버전, 입찰 원장·결과 Outbox와 같은 트랜잭션에 반영한다. 승인 입찰의 변경이 롤백되면 유효 상한도 바뀌지 않는다. 거절·이미 확정된 요청의 재수신은 유효 상한을 바꾸지 않는다.
- 전환용 컬럼은 기존 행과 호환되도록 nullable로 추가한다. 선두가 없는 경매는 기존 초기 규칙대로 현재가를 초기 기준으로만 사용하고, 종료 경매는 활성 Redis 상태로 복구하지 않는다. 선두가 있는 기존 활성 경매의 미기록 값은 자동 상한·현재가의 추정치로 채우지 않는다.
- 이번 로컬 전환은 **미기록 상한을 가진 선두 있는 활성 경매가 없는 검증 환경**을 사용한다. 실행 전 조건을 확인하고, 조건이 맞지 않으면 기존 데이터를 삭제하거나 Redis를 초기화하지 않고 전환을 멈춘다. 미기록 값을 복구 중 만났다면 추정해서 새 상태를 쓰지 않는다. 기존 실데이터의 별도 이행이나 혼합 버전 롤아웃은 이 PR의 승인 범위가 아니다.

## B. 정산과 복구 계약

1. 직접·자동 입찰은 지금처럼 Redis Lua 안에서 원자적으로 계산한다. 정산은 Redis 응답의 유효 상한을 승인 결과와 함께 기존 PostgreSQL 쓰기 경계에서 저장한다. 저장용 상한을 공개 이벤트 DTO로 옮기지 않는다.
2. Redis 상태가 유실됐으면 복구가 읽은 확정 가격·선두·유효 상한·마감·버전과 기존 자동입찰 설정을 사용한다. 경매에 저장한 유효 상한 대신 자동입찰 설정을 참조하지 않는다.
3. 미기록 상태나 가격보다 낮은 유효 상한처럼 확정 상태를 신뢰할 수 없다면 복구를 실패로 남기고 해당 가정으로 입찰을 확정하지 않는다. 진단에는 경매 식별자·오류 종류만 남기고 상한 값은 남기지 않는다.
4. 경매가 이미 종료된 경우 기존 종료 경계를 유지한다. [#417 마감·정산 경합](https://github.com/dev-baek/bidflow/issues/417)의 우선순위, Kafka 재처리 방식, 5분 연장 정책은 바꾸지 않는다.

## S/I. 변경하지 않는 화면과 운영 범위

공개 상세, 검색·WebSocket·Kafka 응답 및 브라우저 상태는 변경하지 않는다. 유효 상한은 API 응답·공개 이벤트·검색 인덱스·로그에 포함하지 않는다. Docker 기반의 격리된 로컬 테스트에서 검증하며 AWS·공유 Redis 초기화·신규 k6 실험은 포함하지 않는다.

## T. 구현 전 실패 테스트와 완료 기준

| 사례 | 확인할 결과 |
|---|---|
| 과거 자동 상한이 유효 상한보다 작거나 큰 혼합 입찰 이력 | 같은 확정 상태와 서버 시각에서, 무중단 실행과 해당 경매 Redis 상태 복구 실행의 다음 승인·거절, 가격·선두·마감·버전이 동일하다. 가격이 역행하지 않는다. |
| 승인 정산의 쓰기 실패와 같은 요청 재수신 | 롤백 시 원장·경매·유효 상한·Outbox가 함께 이전 상태를 유지한다. 재수신해도 확정 결과는 한 번만 남는다. |
| 기존 행·미기록 상한·이미 종료된 경매 | 마이그레이션으로 기존 공개 결과가 바뀌지 않는다. 선두 있는 활성 행에 상한이 없으면 추정 복구하지 않고, 종료 행에는 활성 상태를 만들지 않는다. |
| 공개 계약 | 공개 DTO와 결과·검색 이벤트에 유효 상한이 들어가지 않는다. |

먼저 PostgreSQL과 Redis를 함께 사용하는 회귀 테스트에서 유실 여부만 달리한 두 경로가 다른 결과를 내는 것을 확인한다. 구현 뒤 같은 테스트와 `make verify`, `make verify-integration` 결과를 남긴다.
