# 집중 부하 SQL 실패 분류와 부분 화면 증적 보존

- 상태: 검토 대기. 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)를 사용한다.
- 기반: [브라우저 수렴 사양](issue-019-load-browser-convergence.md), [#302 첫 실행 결과](../reports/issue-019-load-browser-convergence.md).

## 발견한 사실과 남은 질문

#302의 본 실행은 1,000건을 모두 접수했지만 첫 `SCOPED_SQL`이 4.224초 후 exit 1로 종료됐다. PostgreSQL 로그는 4초 statement timeout을 확인했다. 두 공개 frame은 남았으나 SQL 성공 뒤에만 DOM 시각을 내보내는 구조라 화면 확인 여부는 보고할 수 없다. 복원 후 같은 경매의 조회는 약 231ms에 끝났으며 원장과 최종 공개 eventId가 일치했다.

11월 23일 02:46:55 JST에 같은 경매의 기존 SQL을 `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)`으로 한 번 읽었다. 기존 read-only transaction·4초 statement·5초 호출 상한을 유지했고 API PID 94652 및 readiness UP을 확인했다.

| 관측 | 현재의 실행 계획 |
|---|---|
| 계획·실행 시간 | 3.115ms·40.787ms. 서버의 EXPLAIN 계측값이며 전체 CLI 응답 시간이 아니다. |
| 요청과 원장 | 각각 bitmap index 경로, 실제 1,000행 |
| Outbox | 순차 스캔, 추정 484행·실제 1,000행, 공유 블록 hit 747·read 0 |
| 요청 CTE와 조인 | 요청 CTE 하위 스캔은 추정 8행·실제 1,000행, 최종 조인은 추정 19행·실제 1,000행. 이벤트 해시 집계의 임시 read/write는 4/26블록. |

이 계획은 부하가 끝난 뒤의 한 표본이며 당시 쿼리 계획·락 대기·I/O 압박을 재현하지 않았다. 순차 스캔과 카디널리티 차이는 최적화 후보를 찾는 근거이지 시간 초과의 원인이나 인덱스 필요성을 입증하지 않는다.

## S. 화면 관측

앱·입찰·구독 동작은 바꾸지 않는다. 관측자 A/B는 기존 방식으로 지정 가격을 실제 DOM에서 확인한 경우에만 시각을 기록한다. 화면 확인에 실패했거나 마감 때 미완료라면 값을 채우지 않는다. 공개 frame 수신과 화면 확인을 따로 표시한다.

## D. 부분 증적과 성공 판정

기존 허용 필드 외에 화면 후보의 역할·경매 ID·도메인 eventId·가격·확인 시각을 저장한다. 같은 역할과 eventId의 최초 DOM 확인만 사용한다. 같은 frame 상한 안에서 수집하고, 종료 시 단조 시계로 경계를 잘라 복제한 증적을 저장한다. 관측기 오류나 SQL 실패로 관측을 종료할 때 이미 완료된 확인만 남기며, 새 조회나 대기를 시작하지 않는다. 늦게 끝난 DOM 대기나 실패한 cleanup이 이미 저장한 기록을 바꾸지 못한다. 관측 종료와 cleanup 결과는 분리한다.

부분 DOM 기록은 최종 승인이라고 부르지 않는다. SQL·최종 frame·DOM·시간 조건이 모두 맞아야 기존 연결 판정을 통과한다. 부분 기록이 있더라도 SQL 실패의 `valid`, `browserObservationValid`, `fullVerified`는 false다. 사후 SQL은 별도 시각을 표시하며 원래 판정을 바꾸지 않는다.

## B. 최소 수정 범위

- 기존 브라우저 관측기의 화면 완료 콜백에서 허용 필드를 기록한다. 소비처는 기존 `finish`와 부분 증적 저장 경계로 한정하며 Playwright 프로세스를 추가하지 않는다.
- `SCOPED_SQL` 경계에서 고정 실패 코드로 서버 쿼리 취소(SQLSTATE 57014), 로컬 프로세스 제한, 출력 파싱 실패, 기타 SQL 호출 실패를 구분한다. 서버 응답에서 57014만 확인되면 포괄적인 쿼리 취소로 분류하고, 모든 취소를 statement timeout이라고 부르지 않는다. 확인되지 않은 오류는 기타로 남긴다. 원문 stderr·SQL·URL·인자·토큰은 저장하지 않는다.
- 쿼리 변경을 검토할 때는 `buildFocusedSql`과 `buildConcurrentSql`의 공용 SQL 경계에서 경매 ID의 중복 조건과 CTE 투영을 우선 살핀다. 요청/원장/이벤트의 전체 경매 집계와 선택된 요청 상세는 서로 다른 계약이다. 이전·후보 쿼리가 정렬 순서를 빼고 같은 JSON을 내며, 같은 경매 fixture에서 실행 계획이나 반복 관측 비용에 개선 근거가 있을 때만 변경한다. 근거가 없으면 기존 SQL을 유지한다. 기본 동시 브라우저·직접 입찰 진단·k6 호출자를 모두 검증한다.

## I. 실행 제한

읽기 전용·4초 statement timeout·5초 프로세스 상한, 부하 종료 후 60초 마감과 기존 전체 상한을 유지한다. 현재 증적으로는 인덱스·마이그레이션·글로벌 PostgreSQL 설정·제한 시간 상향을 정당화하지 않는다. SQL timeout 뒤 부하나 쿼리를 자동 재시도하지 않는다.

이 사양의 병합은 구현과 기존 fixture의 제한된 읽기 전용 대조만 승인한다. 부하 재실행, 새 Fixture/입찰, API 재시작 및 AWS는 범위 밖이다. 다시 실측하려면 별도 승인 범위와 새 증적을 준비한다.

## T. TDD와 완료 기준

1. SQL 실패 뒤 이미 본 화면은 남지만 미완료/늦은 확인은 남지 않는 RED를 작성한다. 두 화면의 성공과 실패·cleanup 누락·잘림·다른 eventId 및 기본 observer 미사용 경로를 검사한다.
2. 가짜 I/O로 서버 취소·프로세스 제한·파싱 실패·일반 호출 실패를 검증하고 민감 문자열이 증적에 없는지 확인한다. 기존 trace 및 종료/복원 판정을 유지한다.
3. SQL 후보가 있다면 빈/부분 경매, 누락·중복 원장/결과, 2개 요청 필터와 범위 밖 경매의 정합성을 검증한다. 기존 smoke·1,000건 fixture는 제한된 읽기 전용 조회로 비교하고 결과/계획을 구분해 보고한다. 순서가 없는 집계 배열은 정렬 후 비교하되 중복은 제거하지 않는다.
4. 기본 `make verify`와 관련 관측 및 호출자 테스트를 통과시킨다. 이후 결과 PR에 재검증하지 않은 범위와 #302 미완료 상태를 남긴다.
