# 동시 두 사용자 입찰의 브라우저 지연 검증 사양

- 상태: #276 승인, #277 순수 판정 병합 완료. [브라우저 수집·SQL 대조 연결 구현](../reports/issue-019-concurrent-collection-implementation.md)을 진행했다. 실제 smoke·정식 10회 실측은 아직 완료하지 않았다.
- 기존 이슈: [#19 부하와 장애 검증](https://github.com/dev-baek/bidflow/issues/19). Browser 실행 기반은 [#20 E2E](issue-020-e2e.md)를 재사용한다.
- 선행 결과: [순차 화면 측정](../reports/issue-019-local-outbox-delay.md), [동시 요청의 DB 관측](../reports/issue-019-final-settlement-observation.md), [기본 검증과 CI](../reports/issue-003-verification-ci.md).

## 목적과 범위

로컬 100ms Outbox 설정에서 순차 화면 관측 P95는 약 430ms였지만, 두 사용자가 결과를 기다리지 않고 입찰할 때의 화면 지연은 별도 검증이 필요하다. 기존 순차 테스트의 정의나 결과를 바꾸지 않고 **동시 제출 2건씩 10회, 총 20건**의 작은 실험을 추가한다. 20건 전체 동시 요청, k6 지속 부하, AWS 성능을 의미하지 않는다.

앱의 가격 규칙·API·DB schema·Scheduler·timeout 정책은 변경하지 않는다. 기존 Playwright와 Node 표준 라이브러리 및 순수 판정 함수를 사용하며 새 의존성은 추가하지 않는다.

## S. 두 사용자 시나리오

각 회차는 새 상품·활성 경매 하나를 등록한다. 시작가는 10,000원이고 고정 업무 시각은 마감 10분 전이다. 두 사용자는 서로 분리된 Chromium context에서 같은 경매를 열고 공개·개인 구독과 초기 화면을 준비한다. 준비 시간은 지연 표본에 넣지 않는다.

사용자 A는 11,000원, 사용자 B는 12,000원을 직접 입찰한다. 입력을 모두 완료한 뒤 두 click 작업을 함께 시작하고, 한 사용자의 결과를 기다려 다른 요청을 제출하지 않는다. 각 요청에는 서로 다른 멱등 키를 사용한다. 회차별 경매가 새로 생성되므로 이전 최고 입찰자의 SELF_BID나 이전 회차 가격이 다음 회차에 영향을 주지 않는다.

- B의 12,000원 입찰은 승인되어야 한다.
- A는 먼저 처리되면 승인, B 뒤에 처리되면 BID_TOO_LOW 거절이 허용된다. 정상 업무 거절을 HTTP 실패나 미완료로 세지 않는다.
- 두 화면의 최종 공개 가격은 12,000원이어야 한다. 개인 화면은 자신의 요청에 해당하는 승인 또는 거절을 표시해야 한다.
- 두 개인 frame은 처리 당시 판정이다. A의 과거 승인 frame의 isHighestBidder를 최종 승자 판정으로 쓰지 않는다. 최종 승자는 원장과 경매 상태로 별도 확인한다.

동시에 유지하는 입찰자 context는 최대 2개이며 회차 사이 정리 또는 안전한 재사용을 한다. 전체 회차는 worker 1개, retry 0으로 실행한다. 회차 간에는 앞선 두 요청과 화면 검증을 완료한다.

## D. 요청별 증적과 정합성

표본 키는 runId·회차·auctionId·bidRequestId다. 기존 파서로 검증한 개인 frame만 사용하며 다른 요청·다른 경매의 frame이나 중복 frame으로 표본을 완료하지 않는다. 같은 요청이 양쪽 사용자 채널에 노출되면 격리 실패로 기록한다.

회차 종료 뒤 해당 경매와 두 요청만 읽는 SQL로 다음을 확인한다.

1. HTTP는 두 건 모두 202 RECEIVED이며 요청 ID가 유효하고 전체 실행에서 중복되지 않는다.
2. 요청·원장·결과 Outbox가 각 2건이고, 요청당 원장과 BidAccepted/BidRejected 결과는 각각 1건이다. AuctionExtended 등 다른 이벤트는 결과 중복으로 세지 않는다.
3. 요청 상태·원장·결과 이벤트와 개인 frame의 판정이 일치한다. 승인 1~2건, 거절 0~1건만 허용한다.
4. 요청 ID로 원장과 결과 Outbox payload를 연결하고, 승인 결과의 auctionVersion 순으로 가격이 증가하는지 확인한다. 원장에 version 컬럼이 있다고 가정하거나 같은 시각의 decided_at만으로 처리 순서를 추정하지 않는다.
5. 최종 ACTIVE 경매의 가격은 12,000원, 승자는 B다. 최종 version은 초기 version에 승인 건수를 더한 값이고 마지막 승인 원장과 일치한다. 종료 시각은 변하지 않는다.

원본은 허용된 식별자, 금액, 판정, version, 상대 시각과 집계만 저장한다. Token·세션·전체 frame·전체 HTTP 본문·이미지 URL은 커밋하지 않는다. 실패 trace/screenshot은 기존 로컬 보관 정책을 따른다.

## B. 측정 정의

| 지표 | 같은 Playwright runner의 단조 시계 기준 |
|---|---|
| 시작 | 해당 사용자 click 호출 직전 |
| POST 관측 | 해당 페이지의 실제 입찰 POST request 이벤트 수신 |
| 접수 관측 | 해당 POST의 응답 본문 수신 완료 |
| 개인 결과 관측 | 일치하는 requestId·auctionId의 개인 frame 최초 수신 |
| 회차 화면 수렴 | 두 개인 결과의 승인/거절 안내와 양쪽 공개 12,000원을 모두 확인한 시각 |

개별 화면 지연은 각 요청의 시작부터 공통 회차 화면 수렴까지다. 한 사용자의 결과만 확인하는 지연이나 순간 paint 시간이 아니며 Playwright polling 비용을 포함한다. 개인 결과 지연과 화면 수렴 지연은 별도 P50/P95/P99로 기록한다. 서로 다른 시계나 서로 다른 백분위를 빼거나 더하지 않는다.

두 POST 관측의 시각 차이와 각 회차의 동시성 유효 여부도 기록한다. 두 번째 POST가 첫 개인 결과보다 먼저 관측된 회차만 이 실험의 동시 제출 회차로 인정한다. 두 click을 Promise.all로 시작했다는 사실만으로 동시성을 선언하지 않는다. 조건을 충족하지 못한 회차는 삭제·자동 재시도하지 않고 동시성 미충족으로 남긴다. Kafka의 실제 처리는 파티션 안에서 순차적이며 이 조건이 병렬 정산을 의미하지 않는다.

frame 수집은 click 전에 시작하고 HTTP 응답보다 먼저 도착한 개인 결과도 requestId로 나중에 연결한다. 낮은 입찰이 승인된 뒤 더 높은 공개가로 바로 넘어가더라도 중간 11,000원 화면을 반드시 관측해야 한다고 요구하지 않는다. 최종 12,000원 수렴과 개별 판정을 검증한다. 낮은 입찰 거절 frame의 currentPrice를 제출액 11,000원과 비교해서 버리지 않는다.

## I. 로컬 실행 경계

새 플래그 BIDFLOW_E2E_CONCURRENT_LATENCY=1로 기존 순차 실험과 구분한다. 플래그 없는 skip을 측정 완료로 세지 않는다. 기본 make verify에는 서비스를 요구하는 이 실험을 넣지 않는다.

기존 local,e2e API·Vite·Docker와 로컬 100ms 프로필을 사용한다. health/readiness·구독 준비 및 실제 유효 설정을 기록하되 health나 Lag 0만으로 업무 준비를 보장하지 않는다. 기본 서비스와 실행 중 API를 식별하고, 재시작이 필요하면 기존 인자와 실행 상태를 기록해 검증 후 복원한다. 다른 부하·Clock 변경과 동시에 실행하지 않는다.

한 회차의 click 이후 관측 상한은 10초, 전체 테스트 상한은 준비를 포함해 300초다. 느린 성공을 빠른 값으로 치환하거나 timeout을 늘려 목표를 맞추지 않는다. 첫 실패 시 이미 수집한 표본과 미실행 회차 수를 보존하고 종료한다. P95 초과만으로는 수집을 중단하지 않고 가능한 전체 10회를 기록한다.

경매는 새 Fixture로 만들며 기존 데이터·Redis 키·볼륨·offset을 초기화하지 않는다. AWS 자격증명, 원격 endpoint, 실제 Cognito 사용자와 리소스 명령은 사용하지 않는다.

## T. 구현 순서와 판정

1. 순수 판정의 RED: 잘못된 요청/경매·결과 중복·양쪽 개인 채널 누출·고가 거절·허용하지 않은 거절 사유·역전된 시각·동시성 미충족·빈 표본·미완료를 성공으로 세지 않는 테스트를 먼저 작성한다.
2. 최소 GREEN: 기존 frame 파서와 백분위 함수를 재사용한다. 순차 측정 전용 matchesObservedBid의 ACCEPTED/제출액 일치 계약은 변경하지 않고 새 동시 판정을 분리한다.
3. 가짜 I/O로 HTTP 실패·응답 전 frame·timeout·관측 순서 경계를 확인한 뒤 flag 기반 E2E를 연결한다. 공유 모듈 변경은 기존 순차 측정 테스트도 통과해야 한다.
4. 로컬 한 회차 smoke 후 별도 새 Fixture로 정식 10회 실행한다. smoke와 본 실행을 합쳐 20건을 만들지 않는다. Kafka Lag 전후와 SQL 정합성을 따로 수집한다.
5. 10회 동시성 조건, 20건의 접수·개인 판정·화면 수렴 및 모든 원장 불변식이 충족된 실행만 전체 성공이다. nearest-rank 화면 P95 2,000ms 이하를 별도 성능 판정으로 표시한다. 승인/거절별 건수와 지연도 함께 기록한다.

표본이 부족하거나 동시성 조건이 하나라도 미충족이면 부분 결과와 이유를 남긴다. 완료 표본 백분위로 전체 성공을 선언하지 않으며, 실패를 0ms로 넣지 않는다. 한 실행의 20개 표본은 10개 회차에 묶여 있으므로 독립된 대규모 부하 결과로 일반화하지 않는다.

결과 보고서에는 코드 commit, 도구·호스트 환경, 프로필/Outbox 간격, 실행 시각, 수집 해상도, 전체/완료/미완료/동시성 미충족 건수, SQL 결과와 한계를 기록한다. 정확한 DB 커밋 시각, 자동입찰·장애·AWS 지연이나 1,000건 동시 HTTP 기준을 달성했다고 주장하지 않는다.
