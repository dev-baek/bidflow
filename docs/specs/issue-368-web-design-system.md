# BidFlow 경매 마켓 UI 개편 사양

- 상태: 경매 마켓 방향 개정안
- 상위 이슈: [#368 전 화면 UI 개편](https://github.com/dev-baek/bidflow/issues/368)
- 범위: React·TypeScript·Vite와 기존 CSS 및 공통 UI를 재사용한다. 입찰·정산·인증 계약, 업로드 규칙, DB 스키마, AWS 배포는 변경하지 않는다. 공개 상품 사진의 읽기 계약만 #390에서 별도로 검토한다.

## S. 화면과 사용자 흐름

BidFlow의 첫 화면은 설명용 랜딩 페이지가 아니라 경매를 찾는 곳이다. 구매자는 상품 사진과 가격을 비교한 뒤 입찰하고, 판매자는 사진부터 추가해 출품 조건을 작성한다. [Yahoo! 오쿠션 홈](https://auctions.yahoo.co.jp/)의 검색·카테고리 탐색, [검색 결과](https://auctions.yahoo.co.jp/search/search?p=%E3%82%AB%E3%83%A1%E3%83%A9)의 조건 좁히기, [출품 안내](https://auctions.yahoo.co.jp/guide/guide/sell02.html)와 [입찰 안내](https://auctions.yahoo.co.jp/guide/guide/bid02.html)의 정보 순서를 참고한다. Yahoo!의 로고·이미지·문구는 사용하지 않고, BidFlow의 브랜드와 한국어 UI를 유지한다.

거래 화면은 큰 장식 카드보다 좁은 여백, 얇은 구분선, 비교 가능한 상품 정보에 비중을 둔다. 제목이나 필터가 화면 대부분을 차지하지 않게 한다. 문구는 사용자 상태와 다음 행동을 설명하며 내부 이슈 번호, 헤더 이름, 스토리지 키는 표시하지 않는다.

| 화면 | 우선 정보와 행동 | 필수 화면 상태 | 이슈 |
|---|---|---|---|
| 로그인 `/login`, 인증 콜백 `/auth/callback`, 보호 라우트 | 로그인 방법과 다음 행동. 로컬에서는 “테스트용 ID를 입력하세요”; Cognito에서는 로그인 시작·재시도만 노출 | 빈 ID, 인증 중·실패·만료, 보호 경로 진입과 기존 리다이렉트 | #370 |

### 데스크톱 디자인 시안 (리뷰용)

아래 이미지는 정보 순서와 화면 밀도를 검토하기 위한 생성 시안이다. 상품 사진·가격·날짜·검색 조건은 예시이며, 실제 구현 범위와 동작은 본 사양 및 각 이슈를 따른다.

- [출품 시안](../design-previews/marketplace/seller.png) — #391, #392: 사진 추가와 대표 사진을 먼저 보여주고, 상품 정보와 경매 조건을 순서대로 배치한다.
- [검색 시안](../design-previews/marketplace/search.png) — #372: 보조 필터는 왼쪽에 두고, 결과 영역은 사진·상품명·현재가·남은 시간을 비교하는 데 집중한다.
- [경매 상세 시안](../design-previews/marketplace/detail.png) — #374: 왼쪽에서 사진을 확인하고, 오른쪽에서 현재가·마감·입찰을 한눈에 확인한다.

### 출품 화면 구조

```text
공통 헤더 → 출품
사진        [사진 추가] [대표 사진] [다른 사진…]
상품 정보   상품명 / 설명 / 카테고리 / 상품 상태
경매 조건   시작가 / 시작 시각 / 마감 시각 [2026-12-01] [21:30] (UTC) / 기존 경매 옵션
하단 행동   [상품 등록] → 성공 시 [경매 상세 보기]
```

사진은 선택 즉시 로컬 미리보기를 보여주되 서버 업로드 완료와 구분한다. 대표 표시와 순서는 기존 저장 계약을 따른다. 사진 제한·필수 입력·경매 규칙은 그대로 둔다. 모바일은 같은 순서로 한 열에 표시하며, 고정 제출 바를 적용하더라도 마지막 필드나 키보드 포커스를 가리지 않는다.

**마감 시각(#392):** 시안에는 날짜만 표시되어 있지만, 실제 출품 폼에서는 날짜와 시·분을 모두 설정할 수 있어야 한다. 기존 출품 폼의 UTC 기준을 입력 옆에 명시하고, 선택한 시간을 자정으로 바꾸지 않고 분 단위까지 등록 요청에 전달한다. 테스트에서는 자정이 아닌 마감 시각을 입력해 요청 값에 시·분이 보존되는지 확인한다. 기존 마감 검증 및 입찰 시 자동 연장 규칙은 유지한다.

## S. 디자인 토큰과 공통 컴포넌트

흰색 정보 영역, 남색 본문, 파란색 주요 행동을 유지한다. 공통 토큰을 사용하되 거래 화면에서는 페이지 제목 24/32, 비교 카드 제목 16/24, 카드 가격 20/28, 상세 현재가 28/36을 기본으로 한다. 반복 행과 카드 내부 간격은 8–16px, 주요 구역 사이는 24px부터 시작한다. 정보 밀도를 높이기 위해 주요 터치 영역의 44px 기준을 줄이지 않는다.

- **버튼과 링크:** primary, secondary, ghost의 세 가지를 기본으로 한다. 실제 위험 동작이 있을 때만 오류 색을 쓴다. 로딩은 레이블과 함께 보이고 중복 요청을 막는다. 페이지 이동은 링크, 폼 제출과 상태 조작은 버튼으로 둔다.
- **입력:** 입력·셀렉트·텍스트 영역·파일 입력에 라벨/도움말/인라인 오류를 연결한다. placeholder는 라벨을 대체하지 않는다. 첫 오류에 접근할 수 있게 하고 오류 때문에 작성한 값이나 성공한 업로드가 사라지지 않게 한다.
- **상태와 카드:** 로딩·빈 상태·오류·성공은 공통 패턴을 사용한다. 배지는 색만으로 뜻을 전달하지 않는다. 상품 카드의 이미지 영역은 4:3, 잘림은 썸네일에만 적용한다. 이미지 주소가 없거나 로딩에 실패하면 같은 비율의 대체 영역을 렌더링한다.

## D. 표시 데이터와 보호 경계

- #390에서 목록 대표 사진과 상세 사진 조회를 정의한다. 서버가 공개 출품인지, 사진이 해당 상품/경매에 실제 등록돼 있는지 확인한 뒤에만 짧은 수명의 읽기 주소를 제공한다. 브라우저가 임의 경로를 보내 서명받지 못한다. S3·SeaweedFS는 비공개를 유지하고, 브라우저가 키로 URL을 조립하지 않는다. 미리보기가 없거나 실패한 항목만 대체 영역을 사용한다.
- 서버의 가격·상태·종료 시각을 기준으로 한다. 남은 시간은 보조 표시이며 종료 판정에는 쓰지 않는다. 서버가 연장된 종료 시각을 반환하면 교체한다. 화면에 시간대를 명시하고 기존 검색 요청의 UTC 변환 방식은 바꾸지 않는다.
- HTTP 접수, 입찰 승인/거절, 경매 종료, 본인 낙찰/패찰은 각각 다른 상태다. 요청 당시 최고 입찰자를 현재 최고 입찰자나 최종 낙찰자로 표현하지 않는다. 비공개 결과는 인증된 본인에게만 그대로 제공하고, 세션 전환 시 이전 결과가 남지 않아야 한다.
- 읽기 전용 사진 계약을 제외한 API·DB 스키마, 검색 cursor, JWT/PKCE, 입찰 멱등성, 웹소켓 재연결과 마감 연장 규칙은 유지한다. 실제 연결 상태를 관측할 수 없으면 “연결됨”을 표시하지 않는다. 배송·결제·판매자 평가·찜·입찰 횟수 등 지원하지 않는 기능과 데이터는 이번 범위에서 제외한다.

## B. 프런트엔드 적용 방식

1. #369에서 `apps/web/src/styles/tokens.css`에 색·폰트·공간·크기 변수를 선언하고 기존 `styles.css`에서 한 번만 불러온다. 브레이크포인트는 CSS 사용자 정의 속성으로 미디어 쿼리를 만들지 않고, 합의한 두 값만 스타일에서 사용한다.
2. Button, Field, Badge, 상태 메시지와 페이지 레이아웃은 공유한다. HTML 기본 동작을 살리고, 동일한 마크업·상태가 반복될 때만 React 컴포넌트로 추출한다. 변경한 화면에는 직접 색상 리터럴이나 임의의 버튼 높이를 새로 넣지 않는다. 외부 UI 라이브러리, 웹폰트 CDN, 다크 모드는 이번 범위 밖이다.
3. 기존 로그인·오류 화면은 재사용한다. 다음은 출품 #391 → #392로, 가짜 상품 사진 fixture를 사용한 모바일·데스크톱 미리보기에서 밀도와 순서를 먼저 확인한다. 구매 흐름은 #390 읽기 계약 → #372 목록·#374 상세 → #375 입찰/결과로 진행한다. #393 홈·헤더는 목록 패턴을 맞춘 뒤 적용한다. 페이지 상태는 기존 reducer/adapter를 재사용한다.

## T. 검증과 마감 기준

- 화면별 PR: 현재 상태를 고정하는 테스트부터 작성한다. React Testing Library/Vitest에서 역할과 접근 가능한 이름, 키보드/오류/비활성 상태, 성공·실패·재시도와 늦은 응답을 해당 화면에 맞게 검증한다.
- 통합 #376: 320/390/768/1280px에서 가로 넘침과 화면 잘림이 없어야 한다. Tab/Shift+Tab·Enter로 주요 경로를 확인하고, 포커스가 헤더 등에 가려지지 않아야 한다. 일반 텍스트는 4.5:1, 큰 텍스트와 필수 컨트롤 표시/경계는 3:1을 기준으로 삼는다. 44px 주요 터치 목표는 프로젝트 기준이다. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- 기존 Playwright 핵심 흐름(로컬 로그인 → 등록 → 검색/상세 → 직접·자동 입찰 → 종료 시 공개/개인 결과)과 `make verify`를 확인한다. Cognito는 로컬 대역으로 성공·콜백 실패·만료를 확인하며 실제 AWS 인증 성공으로 표기하지 않는다.
