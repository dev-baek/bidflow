# 정산 Outbox 조회 비용 비교 사양

- 상태: 호출 점검 후 두 규모의 격리 비교 완료. 확장 사례의 전체 조회 중앙값 개선이 20% 기준에 못 미쳐 인덱스를 적용하지 않는다. [최종 비교](../reports/issue-019-settlement-outbox-comparison.md)와 [첫 실행의 미완료 결과](../reports/issue-019-settlement-outbox-index.md)는 별도로 남긴다. 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)의 후속 작업이다.
- 근거: [#316 실측](../reports/issue-019-settlement-gate-live.md), [중복 조건 비교](../reports/issue-019-scoped-sql-plan-diagnosis.md), [Outbox 실행 계획](issue-019-scoped-sql-reliability.md#발견한-사실과-남은-질문).

#316은 Kafka Lag 0과 입찰 완료 1,000건을 확인한 뒤에도 정산 SQL이 PostgreSQL의 4초 제한으로 취소됐다. 부하가 끝난 뒤 다른 1,000건 경매의 기존·후보 SQL은 약 32ms였고 두 계획 모두 Outbox를 순차 스캔했다. 이 차이만으로 취소 원인을 판단할 수 없다. 이번에는 **다른 경매의 이벤트가 늘어날 때, 현재 경매의 정산 이벤트만 찾는 부분 인덱스가 전체 조회 비용을 실제로 줄이는지** 한 가지 변수만 바꿔 확인한다.

## S. 화면과 성공 판정 유지

앱 화면·공개 구독·입찰 동작은 바꾸지 않는다. 최종 승인 eventId·version·가격·마감이 A/B의 frame 및 DOM과 맞아야 하는 기존 판정도 그대로다. 이번 비교는 DB 조회만 대상으로 하므로 #316의 부분 화면을 최종 승인으로 확정하거나 전체 성능 검증을 통과로 바꾸지 않는다.

## D. 비교할 인덱스와 데이터

현재 Outbox의 발행 대기 인덱스는 `published_at IS NULL`인 행을 찾는다. 정산 조회는 이미 발행된 결과도 읽으므로 그 인덱스를 이 용도로 쓸 수 없다. 기존 조회의 `topic`·`event_type` 조건에 맞춘 [PostgreSQL 부분 인덱스](https://www.postgresql.org/docs/17/indexes-partial.html) 한 개만 후보로 둔다. 요청·원장·Outbox 전체 카운트와 각 요청의 상세 데이터를 구성하는 SQL은 그대로 실행한다.

```sql
CREATE INDEX ix_outbox_bid_result_aggregate
  ON outbox_event (aggregate_id)
  WHERE topic = 'bid-event'
    AND event_type IN ('BidAccepted', 'BidRejected');
```

실제 경매나 요청을 복사하지 않는다. 합성 fixture에 승인·거절이 섞인 대상 경매 1,000건과 발행 여부가 다른 결과를 만든다. 작은 경우에는 무관한 Outbox 이벤트 2,000개, 확장 경우에는 100,000개를 추가한다. 무관 이벤트의 절반은 다른 경매의 입찰 결과, 나머지는 요청 명령·상품 이벤트 등 인덱스 대상 밖의 이벤트로 구성한다. 각 규모에서 인덱스 외에는 두 군의 스키마·데이터·통계 갱신 절차를 같게 유지한다. 두 규모는 재현용 가정이며 운영 데이터 분포의 추정치는 아니다.

## B. 비교 방법과 채택 조건

- 현재 SQL을 그대로 사용한다. 1,000건 조회와 두 요청 상세 조회에서 경매 상태·전체 카운트·요청별 원장/이벤트·최종 승인 결과를 비교한다. 두 요청 경로의 상세 행은 2개여도 카운트는 여전히 경매 전체여야 한다. 배열 순서만 정규화하고 중복은 제거하지 않는다.
- 각 규모에서 동일한 준비 조회 뒤 기존/후보 실행 순서를 번갈아 6쌍 측정한다. [실행 계획](https://www.postgresql.org/docs/17/sql-explain.html)의 Outbox 접근 경로·스캔 행·버퍼와 일반 조회의 프로세스 경과를 분리해 기록한다. 플래너 설정이나 캐시를 강제로 바꾸지 않는다. 취소·마감은 집계에서 조용히 제거하지 않고 그 비교를 미완료로 남긴다.
- 확장 사례에서 플래너가 자연스럽게 후보를 고르고, Outbox 접근 노드의 공유 블록 접근(hit + read)이 절반 이하로 줄며, 프로세스 경과 중앙값도 20% 및 10ms 이상 줄 때만 개선 후보로 남긴다. 블록 기준은 스캔 비용이 실제로 줄었는지, 시간 기준은 그 차이가 조회 전체에도 보이는지 확인하기 위한 이번 실험의 기준이다. 실제 검증의 4초·5초·60초 제한을 대체하지 않는다.
- 작은 사례의 조회와 대표 정산 이벤트 삽입·발행 처리의 중앙값이 기존 대비 10% 또는 5ms 중 큰 쪽을 넘겨 악화되면 보류한다. 대표 쓰기 비교는 읽기와 분리하고 동일한 쓰기를 양쪽에 적용하며, WAL 양과 후보 인덱스 크기도 남긴다. 합성 확장 사례에서만 이득이 나면 실제 채택으로 간주하지 않는다. 검증용 조회의 이득을 위해 운영 입찰에 인덱스 유지 비용을 추가할 근거가 없다면 기존 스키마를 유지한다.

## I. 격리 및 승인 범위

이 사양을 병합한 뒤 기존 Compose와 같은 버전의 별도 PostgreSQL 컨테이너에서만 비교를 진행한다. 기존 Compose 프로젝트·포트·볼륨에 연결하지 않고 결과 원본은 저장소 밖에 둔다. fixture와 DDL은 격리 DB에만 쓰며, 관측 조회는 읽기 전용 트랜잭션·SQL 4초·프로세스 5초로 제한한다. 기존 앱·로컬 DB·Flyway·Kafka·AWS는 건드리지 않는다.

비교 결과가 좋아도 이 사양은 마이그레이션, 실행 제한 변경, API 교체 또는 새 10/1,000건 입찰 부하를 승인하지 않는다. 적용과 실제 부하 재검증은 결과를 보고 별도로 결정한다. 근거가 부족하면 현 상태를 유지하고 원인을 미확정으로 남긴다.

## T. 구현 전 테스트와 완료 기준

1. 먼저 1,000건 fixture로 `judgeFocused`, 전체 요청이 2건인 별도 fixture로 `judgeConcurrentSql`을 통과하는 테스트를 작성한다. 상세 2건을 고르되 전체 카운트가 1,000인 조회는 별도로 출력 동등성을 검사한다. 이벤트·원장 누락 또는 중복, 다른 경매 이벤트 혼입, 최종 eventId·version·가격 불일치가 있으면 비교가 실패해야 한다. 빈 경매와 부분 완료도 두 군에서 같은 구조·실패 판정을 내는지 확인한다.
2. 일정한 시드로 만든 두 규모에서 기존/후보 JSON의 정합성, 계획·버퍼·전체 조회 시간, 쓰기/WAL 및 인덱스 크기를 기록한다. 순서 바뀜은 허용하지만 값·행 수·중복을 감추는 정규화는 하지 않는다. 실행 실패를 성공 표본으로 처리하지 않는다.
3. 관련 SQL/관측 단위 테스트와 `make verify`를 통과시킨다. 결과에는 판정의 근거, 합성 fixture의 한계, 다음 승인 필요 여부를 포함한다. #316을 포함한 이전 실패 판정은 그대로 둔다.
