# 정산 SQL 대기 관측 실제 부하 검증 계획

- 상태: #323 병합 승인 후 스모크와 별도 경매 누적 1,000건을 각각 한 번 실행했다. 본 실행 대기 관측은 확보했으나 정산 SQL 취소로 전체 미통과다. [실측 결과](../reports/issue-019-settlement-wait-live.md). 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)의 범위다.
- 근거: [#316 실제 서버 취소](../reports/issue-019-settlement-gate-live.md), [#320 인덱스 비교](../reports/issue-019-settlement-outbox-comparison.md), [#322 계측과 격리 검증](../reports/issue-019-settlement-wait-observation.md).

#316에서는 Kafka 적체 0과 요청 완료 1,000건을 확인한 뒤 정산 SQL이 서버의 4초 제한에 걸렸다. #322의 관측기는 격리 DB의 합성 잠금은 포착했지만, 이전 부하의 원인을 입증하지 못한다. 이번에는 같은 로컬 부하 조건에서 **정산 SELECT의 성공 여부와, 해당 명령 중 실제로 관측한 대기**를 한 실행에서 별도로 기록한다. 채택 보류한 인덱스와 기존 판정 기준은 바꾸지 않는다.

## S. 화면 검증

기존 Chromium A/B 관측을 유지한다. 같은 경매의 공개 이벤트와 새로고침 없는 DOM에서 스모크 510,000원과 본 실행 50,010,000원을 확인한다. SQL의 최종 승인 eventId·version·가격·마감과 일치해야 통과하며, SQL 실패 뒤 남은 A/B 자료는 부분 관측으로만 보고한다.

## D. 같은 명령에 속한 증거

새 경매·runId·보호된 출력 경로를 단계마다 사용한다. 부하 종료 뒤 새 Kafka Lag 표본의 세 파티션 0 → 해당 경매의 전체·완료 수 일치 → 정산 `SCOPED_SQL` 최대 1회 순서를 [기존 계약](issue-019-settlement-gate-live.md#d-준비-확인의-증거)대로 확인한다. 부하 시작 전 경매 생성용 SQL은 제외한다. 정산 판정은 요청·원장·결과, 두 화면, 후속 Lag 0·DLT 불변을 모두 대조한다.

`settlementWait.command`의 ID와 시작·종료 시각은 위 정산 명령 추적과 같아야 한다. 실행기 단조 시계 기준으로 각 표본의 요청·응답 시각이 모두 그 구간 안에 들어오는지, 시작 간격이 100ms 이상이고 최대 50개인지, 유형별 개수와 활성 표본 수가 실제 표본과 일치하는지 확인한다. 정산 호출이 없으면 0회와 이유를 남기며, 준비용 확인이나 구간 밖 응답을 대기 증거로 세지 않는다.

## B. 실행 옵션과 독립 판정

기존 실행기에 마지막 인자로 `--settlement-waits`만 추가한다. 브라우저 모드, local/system Clock/100ms/INFO와 `runtime.apiMode=INGRESS_TIMING`을 유지한다. 요청·접수·타이밍 로그는 해당 JVM과 경매에서 모든 원래 receipts를 1:1로 연결한다. 중복·누락을 지우지 않는다.

- **기존 검증:** 실행기의 `valid`, `browserObservationValid`, `fullVerified`, HTTP·SQL/화면·계측·정리 결과를 그대로 기록한다.
- **대기 관측:** 정산 명령과 일치하는 구간 내 표본이 하나 이상이고, `status`가 `OBSERVED` 또는 `NO_ACTIVE_SAMPLES`이며 오류 0과 `cleanupVerified=true`일 때 진단 경로를 확인한 것으로 센다. 활성 표본 0은 대기가 없다는 뜻이 아니다. 연결·식별·정리 실패나 구간 누락은 기존 검증과 분리해 기록한다. 실행 도중 오류가 난 표본은 부분 증거로만 남긴다.
- **서버 취소와 해석:** `STATEMENT_TIMEOUT`과 일반 서버 쿼리 취소, 로컬의 5초 프로세스 제한을 구분한다. `LOCK`·`IO`·`CLIENT_WRITE` 등은 관측 시점의 증거다. 비율을 대기 시간이나 CPU 사용으로 환산하지 않는다. 취소가 재현되지 않거나 대기가 포착되지 않아도 #316을 소급해서 설명하지 않는다.

커밋에는 허용된 집계, 상대 시각, 판정과 정리만 남긴다. 대기 관측의 backend PID·태그·SQL 원문·오류 본문은 게시하지 않는다. 실행기가 사용한 시계와 서버 시각을 빼거나 진단 옵션 유무를 성능 A/B로 해석하지 않는다.

## I. 제한과 복원

[기존 로컬 실행 계약](issue-019-ingress-full-verification.md#i-로컬-실행과-복원)을 따른다. 승인된 main의 깨끗한 별도 worktree에서 `make verify`, Node 24·Java 21·Docker/k6/Chromium, API와 컨테이너 readiness를 먼저 확인한다. 정확한 기존 API PID·소유권·인자·jar 해시를 확정할 수 없거나, 다른 부하·Vite 포트 점유가 있으면 시작하지 않는다. 검증 중에만 소유한 loopback API와 Vite를 실행한다.

SQL 4초·프로세스 5초·회복 60초와 기존 브라우저·자원 제한을 유지한다. 관측기 준비도 기존 예산 안의 1초이고, 조회는 재시도하지 않는다. 단계별 브라우저·k6·대기 관측을 정리한 뒤 다음 단계 여부를 결정한다. 종료 시 검증 API·Vite를 정리하고 원래 API의 인자·jar·listen·readiness와 기존 서비스 상태를 확인한다. 기존 데이터·볼륨·Redis key·Kafka offset과 DB 설정은 변경하지 않는다.

## T. 허용 횟수와 중단 조건

| 단계 | 실행과 통과 기준 |
|---|---|
| 스모크 | 새 경매 10건(2 VU × 5회), 최대 1회. 실행기 exit 0, `valid=true`, `browserObservationValid=true`, `fullVerified=false`, 계측 10/10, SQL/화면·순서·후속 Lag/DLT, 대기 관측 경로와 단계 정리를 모두 확인한 경우에만 본 실행을 시작한다. |
| 본 실행 | 별도 경매 누적 1,000건(20 VU × 50회), 최대 1회. P95 < 300ms·오류율 < 1%와 기존 `fullVerified=true`, 계측 1,000/1,000, 대기 관측 및 복원이 모두 맞아야 이번 전체 검증을 통과한다. 실패 단계에서도 확보한 대기 표본과 부분 화면은 별도 판정한다. |

스모크 기준 미달이면 본 실행은 시작하지 않는다. 어느 단계든 자동 재실행, 사후 DB 조회, 제한 완화, 장애 주입은 하지 않는다. #302/#306/#312/#316의 기존 판정은 유지한다. 이 계획은 AWS나 1,000건 전체 동시 HTTP를 승인하지 않는다.
