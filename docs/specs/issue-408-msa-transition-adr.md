# [Issue #408] Auction과 Search의 서비스 경계와 전환 기준

- 상태: 검토 요청. 문서 병합은 로컬 설계 합의이며 실행·배포 승인이 아니다.
- 추적: [#407 MSA 전환](https://github.com/dev-baek/bidflow/issues/407), [#408 ADR](https://github.com/dev-baek/bidflow/issues/408).

## 결정과 대안

현재 Search는 독립 Kafka Consumer Group을 쓰지만, Auction의 PostgreSQL에 직접 접속해 상품·경매·사진을 조합한다. 이 의존성을 둔 채 프로세스만 나누면 원본 스키마 변경과 DB 장애에 여전히 함께 영향을 받는다.

같은 저장소에서 **Auction Core와 Search를 먼저 독립 빌드·배포 단위로 분리**한다. Search는 읽기 모델이라 반영 지연을 허용할 수 있고, 검색 중단이 거래를 막지 않아야 한다는 검증 목표도 명확하다. 현재 구조를 유지하는 대안은 운영이 단순하지만 이 격리를 입증하지 못한다. Catalog를 동시에 분리하는 대안은 기존 상품·경매 등록 트랜잭션과 사용자 성공 조건을 함께 바꾸므로 후속 단계로 둔다.

## S. 사용자와 API 계약

- 기존 `GET /api/v1/listings/search`와 응답·필터·정렬·커서 계약을 유지한다. 일시적인 색인 지연은 허용하지만, 검색 불가는 빈 결과가 아닌 일시 오류로 표시한다. 원장 DB를 대신 검색하지 않는다.
- 상세·입찰·낙찰은 계속 Auction 응답이 기준이다. 검색 결과에 이전 가격이 보이더라도 입찰 승인과 마감 판정에 쓰지 않는다.
- Catalog 분리 시 상품 접수와 경매 생성 완료를 구분한다. 생성 대기·실패·재시도를 표시하며, 생성이 확인되기 전에는 경매가 완료됐다고 표시하거나 경매 링크를 열지 않는다.

## D. 데이터 소유권

| 서비스 | 소유 데이터와 책임 | 다른 서비스의 접근 |
|---|---|---|
| Auction Core | PostgreSQL의 경매·입찰 요청·원장·낙찰·Outbox, Redis 활성 상태. Catalog 분리 전에는 상품·이미지 메타데이터도 소유 | REST 또는 Kafka 계약을 사용한다. 다른 서비스에 JDBC 자격 증명을 주지 않는다. |
| Search | OpenSearch 읽기 모델, 검색 API, 검색 전용 Kafka Group과 처리 상태 | Auction의 테이블·공유 처리 기록을 읽거나 쓰지 않는다. 원본은 버전 있는 공개 이벤트와 원본 소유자가 제공하는 초기 스냅샷으로만 받는다. |
| Catalog (후속) | 상품·공개 상태·이미지 메타데이터 및 객체 경로 권한, 등록 요청과 경매 생성 상태 | Auction은 상품을 계약상의 식별자로 참조한다. 서로의 테이블·교차 FK·직접 조인에 의존하지 않는다. |

입찰 계산·연장·마감·낙찰은 같은 경매의 불변식을 공유하므로 Auction 소유권 안에 둔다. Redis와 검색 색인은 원장이 아니다. Cognito, 기존 WebSocket 경계, 브라우저의 S3 호환 저장소 직접 업로드는 첫 분리에서 변경하지 않는다.

## B. 이벤트 발행과 검색 인덱스 복구

1. Auction은 검색에 영향을 주는 확정 상태와 **공개 검색 스냅샷 이벤트**를 같은 PostgreSQL 트랜잭션에서 Outbox에 기록한다. 키는 검색 문서 식별자인 `productId`, 순서 판정은 그 상품의 단조 증가하는 검색 상태 버전이다. 스키마 버전은 상태 버전과 별개다. HTTP 도착 시각이나 서로 다른 토픽의 전역 순서는 사용하지 않는다.
2. 등록, 일반 입찰 승인, 연장, 종료 및 비공개를 계약에 포함한다. 검색에 필요한 상품·경매 식별자, 가격·상태·마감과 대표 사진 표시 정보만 공개한다. 입찰자 식별자·개인 결과·자동입찰 최대가·저장소 자격 증명은 보내지 않는다. 기존 입찰·실시간 이벤트와 호환성을 유지한다. 상세 필드·금액 범위는 [#409](https://github.com/dev-baek/bidflow/issues/409)에서 [#418](https://github.com/dev-baek/bidflow/issues/418)과 맞춘다.
3. Search는 같은 문서를 버전 조건으로 갱신한다. 같은 버전은 재전달돼도 결과가 같고, 이전 버전은 최신 값을 덮지 못한다. 종료·비공개도 버전과 함께 비노출 상태로 남겨 늦은 이벤트가 상품을 다시 노출하지 못하게 한다. 반영 성공 또는 안전한 무시를 확인한 뒤에만 처리 완료로 센다.
4. 빈 인덱스를 만들 때는 먼저 검색 토픽의 파티션별 다음 오프셋을 기록하고, 그 뒤 Auction이 제공하는 **버전 있는 일관된 스냅샷**을 읽는다. 기록한 지점부터 이벤트를 반영한다. 스냅샷과 겹친 이벤트는 버전 조건으로 처리하고, 필요한 오프셋이 보존 범위를 벗어나면 전환하지 않고 새 스냅샷부터 다시 시작한다. 기존 데이터의 초기 버전과 비공개 상태도 스냅샷 계약에 포함한다.

Catalog 단계에서는 상품 저장과 경매 생성 요청을 연결하되 DB 트랜잭션을 두 서비스에 걸치지 않는다. 생성 요청을 같은 식별자로 재시도할 수 있어야 하고, Auction의 성공·실패 결과로 Catalog 상태가 수렴해야 한다. 전송 방식·상태표·상품 참조가 필요한 검색 이벤트의 책임은 [#412](https://github.com/dev-baek/bidflow/issues/412)에서 결정한다.

## I. 로컬 배포와 전환·되돌리기

- 설계 합의 후 [#416 Redis 복구](https://github.com/dev-baek/bidflow/issues/416)와 [#417 마감·정산 경합](https://github.com/dev-baek/bidflow/issues/417)을 별도 수정 PR로 먼저 다룬다. 새 검색 서비스가 검증되지 않은 거래 결과를 보정하지 않는다.
- [#409](https://github.com/dev-baek/bidflow/issues/409) 이벤트 계약을 먼저 적용하고, [#410](https://github.com/dev-baek/bidflow/issues/410)에서 Search를 별도 이미지·설정·헬스체크로 실행한다. 로컬 Compose에서 Search만 다시 배포해도 Auction을 재시작하지 않아야 한다.
- [#411](https://github.com/dev-baek/bidflow/issues/411)에서 기존 검색 경로를 유지한 채 독립 Search를 별도 인덱스에서 비교한다. 검증 대상 변경의 Outbox 발행과 소비를 확인하고, 상품·가격·마감·공개 상태 및 검색 응답이 일치하면 기존 URL의 라우팅만 바꾼다. Lag 0만으로 전환하지 않는다.
- 미반영·가격 역행·종료 상품 노출·검색 계약 불일치가 있으면 전환을 중단한다. 전환 후 이상이 나면 최신 상태임을 확인한 이전 검색 대상으로 라우팅을 복원한다. 이전 인덱스가 오래됐으면 먼저 따라잡거나 재구축한다. 되돌리는 동안 원장이나 입찰 데이터는 롤백하지 않는다. 안정 확인 전에는 이전 경로·인덱스를 삭제하지 않는다.
- Search 전환 검증 후 Catalog 사양([#412](https://github.com/dev-baek/bidflow/issues/412))을 먼저 병합한다. 구현([#413](https://github.com/dev-baek/bidflow/issues/413))과 화면·E2E([#414](https://github.com/dev-baek/bidflow/issues/414))로 넘어가기 전에 데이터 이행, 이전 경로에서의 쓰기 소유권 전환, 진행 중 요청의 처리와 롤백 기준을 합의한다.
- AWS는 별도 단계다. 배포 단위가 늘어난 기준으로 비용·라우팅·권한과 삭제 계획을 다시 검토하고 [#356](https://github.com/dev-baek/bidflow/issues/356)·[#357](https://github.com/dev-baek/bidflow/issues/357)의 승인을 받기 전 계정 접근·Plan·Apply를 하지 않는다.

## T. 단계별 완료 기준

| 단계 | 로컬에서 증명할 것 |
|---|---|
| Search 배포 | Auction DB 자격 증명 없이 기동·검색한다. Search를 중지한 동안 상품 등록·입찰 접수·정산이 계속되고, 다시 시작하면 검색이 확정 상태를 따라잡는다. |
| Search 전환 | 중복·역순 이벤트와 재구축 중 변경을 포함해 빈 인덱스에서 복구한다. 기존 HTTP 계약과 결과를 대조하고 라우팅 복원도 확인한다. |
| Catalog 전환 | Auction 일시 중단 중 등록 요청을 잃지 않는다. 복구·재시도·응답 유실에도 상품과 경매가 중복 생성되지 않고, 화면의 대기·완료·실패가 구분된다. |

구현 PR은 관련 경계의 실패 테스트부터 작성하고, `make verify`와 해당 통합 검증을 실행한다. Compose 실행 절차, 서비스 중단 전후의 정산·검색 대조, 전환·되돌리기 결과를 기록한다. 이 기준은 k6 부하나 AWS 검증을 통과했다는 뜻이 아니다.

## 기존 결정과의 관계

- [Kafka 선정 ADR](issue-029-kafka-sqs-decision-adr.md): 파티션별 순서, Consumer Group별 재생, 중복 허용 원칙을 유지한다.
- [OpenSearch ADR](issue-027-opensearch-derived-data-adr.md): 검색을 파생 모델로 유지하되, Search의 직접 DB 읽기를 원본 소유자의 스냅샷·공개 이벤트 계약으로 바꾼다.
- [기존 배포 ADR](issue-002-architecture-adr.md)과 [AWS Runbook](issue-017-aws-deployment.md): 현재 배포 구성의 기록이며 이 ADR만으로 프로비저닝을 바꾸지 않는다.
