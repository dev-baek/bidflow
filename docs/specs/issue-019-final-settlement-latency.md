## 목적과 측정 단위

기존 DB 집계의 `processed_at - requested_at`은 Consumer 처리 시작까지의 시간이다. 해당 값을 최종 커밋이나 WebSocket 전달 시간으로 이름만 바꾸지 않는다. **별도 PostgreSQL 연결에서 최종 상태가 보이는 시각**을 관측해 커밋 이후의 결과를 확인한다.

| 지표 | 시작 → 종료 | 해석 |
|---|---|---|
| HTTP 접수 지연 | 클라이언트 전송 직전 → HTTP 응답 본문 수신 완료 | 새 측정기의 수치. k6의 HTTP 타이밍과 동일 지표로 합치지 않음 |
| 정산 최종 관측 지연 | 같은 전송 직전 → 별도 연결 SELECT가 확정 요청·원장을 반환한 직후 | 관측/조회 비용을 포함한 상한. 정확한 커밋 시각은 아님 |
| 서버 처리 시작 지연 | DB `requested_at` → `processed_at` | 기존 측정과 같은 참고값, 커밋 시각으로 간주하지 않음 |
| 브라우저 최종 전달 지연 | 전송 직전 → 개인 결과/화면 갱신 | 이번 대상 아님. 기존 접수→최종 사용자 결과 P95 2초 기준을 달성했다고 주장하지 않음 |

## S. 운영자와 입력

새 UUID로 만든 로컬 활성 시험 경매 하나에 20개 서로 다른 사용자가 각 한 번 직접 입찰한다. 각 요청의 멱등 키는 고유하다. 최대 동시 요청 수는 20, 단일 회차만 실행한다. 기존 k6 20 VU 시나리오는 유지하고 이 측정은 **별도의 제한된 관측 실험**으로 보고한다.

고정된 로컬 API와 BidFlow Compose PostgreSQL만 사용한다. 원격 주소·실제 Cognito 사용자·AWS 연결은 받지 않는다. 상품·경매는 새 Fixture로 생성하며 기존 행, Redis 키, 볼륨을 초기화하지 않는다. 자동입찰·장애·다른 부하 테스트와 동시에 수행하지 않는다.

## D. 확정 판정과 증적

- 응답이 HTTP 202이고 `RECEIVED`와 유효한 `bidRequestId`가 있을 때만 정산 관측 대상에 포함한다. 전송 실패, 잘못된 응답, 중복 ID도 별도 결과로 남긴다.
- 요청 ID와 경매 ID로 좁힌 **읽기 전용** SELECT 한 번에 `bid_request.status`, 해당 요청의 `bid_ledger` 개수·판정, 결과 Outbox를 함께 읽는다. 트랜잭션 Snapshot이 서로 다른 조회 결과를 섞지 않는다.
- `ACCEPTED`/`REJECTED`로 확정되고, 해당 원장 1건의 판정 및 해당 요청의 `BidAccepted`/`BidRejected` 결과 Outbox 1건이 일치해야 확정 표본이다. `AuctionExtended`는 별개 이벤트이므로 결과 Outbox 중복으로 세지 않는다.
- 승인과 정상 업무 거절을 모두 확정 결과로 포함하되 판정별 건수를 따로 남긴다. 가격 역행·원장 중복·최종 승자 불일치는 성능 결과와 별도의 실패다.
- 표본에는 요청 ID, 경매 ID, HTTP 결과, 상대 시각(ms), 최초 최종 관측 시각, 판정·원장/이벤트 수를 보관한다. Token·자격 증명·전체 응답 본문은 기록하지 않는다.

## B/I. 최소 측정기

Node 표준 라이브러리와 기존 Docker/psql을 사용한다. 앱에 관리 API·새 DB 컬럼·커밋 timestamp 기록을 추가하지 않는다. 입력 검증·확정 판정·백분위 계산은 순수 함수로, HTTP·psql·파일·타이머는 실행 경계로 분리한다.

전송과 최종 관측의 상대 시각은 **동일 Node 프로세스의 단조 시계**를 사용한다. 서버 wall clock과 클라이언트 시각을 빼지 않는다. 관측자는 전송 전에 시작하고, 각 완료된 조회 뒤 100ms 간격으로 미확정 요청을 묶어 조회한다. 응답이 도착하기 전에 관측을 놓친 경우까지 포함해 관측 지연은 실제 확정 지연보다 클 수 있다.

조회는 한 번에 하나만 실행하고 조회별 timeout을 둔다. 전체 관측은 첫 전송부터 최대 60초, HTTP 요청에도 timeout을 둔다. 출력에는 실제 조회 시작/완료 상대 시각과 최대 조회 간격을 포함해 Docker/psql 실행 비용과 관측 해상도를 드러낸다. 관측 자체의 부하로 기존 k6 결과와 실행 조건이 다르다는 점을 명시한다.

## T. 실패 테스트와 결과 판정

| 대상 | 확인할 것 |
|---|---|
| 순수 확정 판정 | 요청·원장·결과 이벤트가 일치한 승인/거절만 확정, 미처리·원장 없음/중복·다른 요청 결과는 거부 |
| 백분위 | nearest-rank로 P50/P95/P99 계산, 빈 집합·동일 값·정렬되지 않은 입력·0ms 경계 |
| 측정 경계 | HTTP 실패/timeout·잘못된 ID·중복 ID·DB 실패·지연 응답·60초 만료를 성공 표본으로 기록하지 않음 |
| 로컬 실행 | 새로운 Fixture의 20건 전부에 대한 접수·판정·원장·이벤트와 Kafka Lag 전후, 최종 현재가/승자 확인 |

지연 백분위는 완료 표본 수와 전체 요청 수를 함께 표시한다. timeout은 0ms나 제외된 정상 표본으로 처리하지 않고 미완료 건수·관측 종료까지의 경과 시간을 기록한다. 완료 표본만으로 계산한 수치는 **완료 표본 기준**이라고 표시하고, 미완료가 있으면 전체 성공으로 선언하지 않는다.

P95 목표를 못 맞추거나 관측기가 실패한 회차도 결과와 원인을 남긴다. 본 관측 지연이 2초 이내라도 브라우저 전달 P95 2초의 증거로 대신하지 않는다. 결과에는 commit, 로컬 환경, 실행 시각, Fixture, 관측 간격, 판정/오류/미완료 수와 한계를 기록하고 #19에 연결한다.
