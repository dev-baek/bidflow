# [Issue #227] 본인 낙찰·패찰 결과 조회 사양

- 관련: [#227 본인 낙찰·패찰 결과 조회](https://github.com/dev-baek/bidflow/issues/227), [#20 등록부터 낙찰까지 E2E](https://github.com/dev-baek/bidflow/issues/20)
- 선행: [공개 상세 및 입찰](./issue-213-auction-detail-bid-ui.md), [경매 종료 확정](./issue-015-auction-close.md)

공개 상세의 `낙찰 · 21,000원`은 경매가 판매됐다는 뜻이지 화면을 보는 사람이 낙찰됐다는 뜻이 아니다. 이 작업은 승인된 입찰에 참여한 사용자가 **본인의 최종 결과**를 확인하는 경로만 추가한다. 공개 결과·개별 입찰 요청의 승인/거절은 서로 다른 정보다.

## S. 화면

- 기존 공개 상세는 누구나 동일하게 본다. 로그인한 사용자의 공개 상세가 `ENDED / SOLD`가 된 뒤 별도의 본인 결과를 조회한다. 이 판단에 브라우저 시각이나 마지막 WebSocket 개인 입찰 결과를 쓰지 않는다.
- 조회 중에는 진행 상태, `WON`이면 **내가 낙찰받았습니다**, `LOST`이면 **패찰했습니다**, `NOT_PARTICIPATED`이면 **승인된 입찰 내역이 없습니다**를 표시한다. 활성 경매·유찰·취소 상태에서는 패찰을 표시하지 않는다.
- 비로그인 사용자에게는 개인 조회를 실행하지 않는다. 로그인 만료·실패는 재로그인 안내, 일시적 조회 오류는 **본인 결과 재조회**를 제공한다. 개인 조회 실패로 공개 상세를 지우지 않는다.
- 경매 또는 로그인 주체가 바뀌면 이전 개인 결과를 즉시 비우고 지연 응답을 무시한다. 새로고침 후에는 현재 인증으로 원본을 다시 조회한다. 메모리 기반 로컬 로그인은 새로고침 때 초기화되므로 로컬 인수 테스트는 다시 로그인해 확인한다. 저장소에 토큰이나 개인 결과를 지속 저장하지 않는다.

## D. DB와 분류

PostgreSQL을 원본으로 사용한다. 하나의 조회에서 `auction.status`, `auction_result.outcome`, 인증 주체와 `winner_id`의 일치 여부, 동일 경매·주체의 `bid_ledger.decision = 'ACCEPTED'` 존재 여부를 읽는다. 주체와 경매 ID를 바인딩한다. 최고가, 낙찰자 식별자, 참가자 목록은 조회 모델에 전달하지 않는다. 입찰 접수(`RECEIVED`)와 거절 원장만으로는 참가자가 아니다.

| 서버 상태 | 본인 조건 | 응답 결과 |
|---|---|---|
| `SCHEDULED` 또는 `ACTIVE` | 무관 | `NOT_FINALIZED` |
| `CANCELLED` 또는 `ENDED / UNSOLD` | 무관 | `NOT_APPLICABLE` |
| `ENDED / SOLD` | 승인 원장 없음 | `NOT_PARTICIPATED` |
| `ENDED / SOLD` | 승인 원장 있음, 확정 낙찰자와 주체 일치 | `WON` |
| `ENDED / SOLD` | 승인 원장 있음, 확정 낙찰자와 주체 불일치 | `LOST` |

`ENDED`인데 확정 결과 행이 없으면 정상 상태로 가정하지 않고 조회 실패로 처리한다. 새 테이블·마이그레이션은 추가하지 않는다. 우선 기존 경매 범위의 원장 인덱스를 사용하며, 비용이 확인되기 전 추가 인덱스를 만들지 않는다.

## B. API·인가

`GET /api/v1/me/auctions/{auctionId}/outcome`은 인증 필수다. 공개 GET 허용 패턴인 `/api/v1/auctions/**`의 하위 경로에 두지 않는다. 조회 주체는 서버 인증 Principal에서만 얻는다. 경로·쿼리·본문에 타인 ID를 받아 조회하는 기능은 없다. 기존 개발 ID 헤더는 `local` 프로필에서만 쓰며, 인증이 설정된 배포 환경은 검증된 access token을 사용한다.

성공 응답은 `auctionId`와 `outcome`만 내려준다.

```json
{
  "auctionId": "a045614c-8c21-4eb1-a209-49689dc0d8b1",
  "outcome": "WON"
}
```

인증 없는 요청은 `401`, 인증 후 존재하지 않는 경매는 `404 AUCTION_NOT_FOUND`다. 개인 응답에는 `Cache-Control: no-store`를 적용한다. 낙찰자 ID, 최대가, 개별 입찰가, 인증 주체는 응답과 공유 로그에 추가하지 않는다. 공개 상세 API와 WebSocket 이벤트 계약은 변경하지 않는다.

## I. 실행 범위

기존 Spring Boot·PostgreSQL·React만 사용한다. 새 저장소·캐시·WebSocket 토픽을 만들지 않는다. 현재 브라우저 연동은 로컬 로그인으로 검증하고, Cognito 화면 연결과 실제 AWS 실행은 이 작업에서 수행하지 않는다.

## T. 인수·회귀 검증

1. 순수 분류 테스트에서 위 표의 모든 상태를 검증한다. 읽기 어댑터는 동일 경매에 참여한 서로 다른 주체, 거절만 한 주체, 다른 경매에만 승인된 주체를 구분한다.
2. HTTP 테스트는 익명 거부, 존재하지 않는 경매, Principal 기반 격리, 캐시 금지, 허용 필드만 노출되는 응답을 확인한다. 공개 상세에 개인 결과나 낙찰자 ID가 추가되지 않아야 한다.
3. UI 상태 테스트는 조회 중·결과·오류·재조회와 경매/사용자 전환 후 늦은 응답 무시를 확인한다.
4. 로컬 E2E에서는 기존 두 사용자 자동입찰 경매를 종료하고 A는 `WON`, B는 `LOST`, 승인 입찰이 없는 사용자는 `NOT_PARTICIPATED`를 받는지 검증한다. 공개 가격은 모두 21,000원이다. 새로고침 후 재인증하고 동일 개인 결과를 다시 확인한다. 이미 닫힌 #99를 재개하지 않고 #20에 증적을 연결한다.

구현은 사양 병합 후 실패 테스트부터 시작한다. 판매자 관리, 결제, 배송, 알림은 제외한다.
