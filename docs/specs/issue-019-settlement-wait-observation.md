# 정산 SQL 대기 관측 사양

- 상태: 검토 대기. 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)의 후속 작업이다.
- 근거: [#316 서버 SQL 취소](../reports/issue-019-settlement-gate-live.md), [#318 로컬 호출 제한](../reports/issue-019-settlement-outbox-index.md), [#320 인덱스 비교](../reports/issue-019-settlement-outbox-comparison.md).

#316에서는 Kafka Lag 0과 경매 요청 1,000건의 완료를 확인하고도 정산 SQL이 서버의 4초 제한에 걸렸다. #320에서 부분 인덱스는 읽는 블록을 줄였지만 조회 시간 개선 기준을 넘지 못했다. 따라서 인덱스를 바꾸기 전에 **취소가 난 실행의 정산 SELECT에서 어떤 대기가 실제로 관측됐는지** 기록한다. #318의 5초 Docker·psql 프로세스 제한은 서버 취소와 분리한다.

## S. 기존 화면과 판정 유지

입찰 API, 화면, WebSocket, Kafka는 바꾸지 않는다. 두 브라우저의 최종 이벤트·DOM 대조, 원장 검증, Lag·DLT·HTTP 기준 및 실패 시 부분 기록을 유지한다. 대기 증적은 원장 조회의 성공을 대체하지 않으며, 기본 실행의 성공 기준과 성능 수치에도 합산하지 않는다.

## D. 대상 세션과 증적

진단 옵션을 켰을 때만 정산 조회용 psql 한 개에 임의의 32자리 소문자 16진수 토큰으로 만든 `PGAPPNAME`을 붙인다. 서버의 [`application_name` 연결 설정](https://www.postgresql.org/docs/17/libpq-envars.html)을 사용하며 경매·사용자 ID나 비밀값은 넣지 않는다. DB와 역할이 모두 `bidflow`이고 `backend_type='client backend'`인 정확한 태그의 행만 조회한다. 첫 대상의 PID와 `backend_start`는 메모리에서만 고정해 이후 표본과 대조한다. 시작 전 같은 태그가 있거나, 관측 중 둘 이상이 일치하거나, 재사용으로 세션이 바뀌면 진단은 무효다.

기존 정산 SELECT의 내용은 그대로 유지한다. 진단 경로에 한해 같은 psql 세션의 별도 [`-c` 요청](https://www.postgresql.org/docs/17/app-psql.html)으로 읽기 전용 트랜잭션·제한 설정, 고정 주석을 앞에 붙인 SELECT 한 번, COMMIT 순으로 보낸다. `pg_stat_activity`에서는 고정 접두사가 일치하는지만 불리언으로 계산한다. 연결, BEGIN, SET, COMMIT, 이미 끝난 SELECT는 대기 판정 대상이 아니다. 기본 경로의 SQL과 호출 방식은 그대로 둔다.

증적에는 같은 실행기 단조 시계의 조회 명령 구간, 관측 요청·응답 상대 시각, 대상 상태·대기 분류, 성공·누락·오류 횟수와 최대 표본 간격만 남긴다. PID·태그·SQL 원문·결과 본문·원문 오류·다른 세션 정보는 저장하지 않는다. 서버 취소 여부는 기존 SQLSTATE 분류를 유지하고, 정확한 서버 원문 신호를 확인할 수 있을 때만 statement timeout으로 세분한다. 57014만으로 4초 제한에 걸렸다고 판정하지 않는다.

## B. 수집 순서와 해석

기존의 새 Lag 0 → 경매 요청 수와 완료 수 일치 → 정산 SQL 한 번 순서를 유지한다. 완료 확인 뒤에만 별도의 로컬 관측 psql 한 개를 시작한다. 포트나 커넥션 풀을 추가하지 않는다. 관측기는 동일 역할의 읽기 전용 연결에서 한 번에 한 SELECT만 보내고 표본마다 새 트랜잭션으로 읽는다. [`pg_stat_activity` 문서](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)에 따라 같은 트랜잭션의 조회 시점이 고정되는 것을 피한다.

관측이 준비되면 100ms보다 자주 조회하지 않고, 정산 명령 중 최대 50개를 모은다. 개별 서버 관측 조회는 200ms로 제한한다. 정산 명령 시작과 종료 사이에 요청·응답이 모두 들어온 표본 중, 대상 SELECT가 표시되고 `state=active`인 것만 대기 분류에 쓴다. 연결 준비용 확인과 늦게 도착한 응답은 분류 표본으로 세지 않는다.

| 표본 | 해석 |
|---|---|
| `Lock`, `IO` | 그 순간 잠금 또는 I/O 대기를 관측했다. 누가 막았는지, 대기가 얼마나 지속됐는지는 확정하지 않는다. |
| `LWLock`, `BufferPin`, `IPC`, `Client` 등 | 각각 분리해 기록한다. `ClientWrite`는 서버의 결과 전송 대기이며, Docker 전체 경과 시간과 동일하지 않다. |
| active이고 대기 값이 비어 있음 | 그 표본에 노출된 대기가 없다. CPU 사용이나 대기 부재를 증명하지 않는다. |
| 대상 미검출, 비활성, 관측 오류 또는 창 일부 누락 | 관측 공백으로 표시한다. 빠르게 끝난 SELECT를 놓칠 수 있다. 실패와 0건을 성공으로 바꾸지 않는다. |

결론은 대기 유형별로 **관측한 표본 수**로 낸다. 이를 쿼리 시간의 비율이나 연속 대기 시간으로 환산하지 않는다. 관측을 위해 정산 명령을 반복하거나 취소 뒤 새 조회를 시작하지 않는다.

## I. 시간 제한과 격리

관측 시작은 기존 회복 마감 안에 1초 준비와 5초 본 호출 여유가 있을 때만 시도한다. 준비는 1초에 끝내고 정산 시작 직전에 기존 5초 예산을 다시 확인한다. 관측을 시작할 수 없으면 진단만 미확보로 표시하고 기존 수집 흐름의 마감을 따른다. 관측 세션이 도중에 실패해도 본 조회를 재호출하거나 기존 SQL 판정을 덮어쓰지 않는다. 관측기 자체의 정리 실패는 별도 실패로 남기며 실행을 인수인계할 때 누락하지 않는다.

정산 SQL 4초·프로세스 5초와 부하 뒤 회복 60초 제한을 유지한다. 정산 종료 또는 전체 마감에서 관측 입력을 닫고, 필요하면 소유한 관측 프로세스만 정리한다. 관측이 권한 부족이나 `track_activities` 비활성으로 불가능하면 중단한다. 역할 부여, 전역 PostgreSQL 설정·로그 수준 변경, 운영 락 주입, 인덱스·쿼리 최적화는 범위 밖이다.

사양 병합 후 허용하는 범위는 실행기 계측 구현과 **네트워크·공개 포트·기존 볼륨이 없는 격리 PostgreSQL 17.5**의 합성 검증이다. 기존 로컬 DB에서의 실측, API 교체, 새 10/1,000건 입찰 부하, AWS는 별도 승인 범위다.

## T. 구현 전 테스트와 완료 조건

1. 가짜 시계·I/O로 옵션 미사용 시 기존 경로가 같고, 옵션 사용 시에도 조회는 최대 1회임을 검증한다. 이전 표본·다른 태그·PID 교체·중복·다른 문장·늦은 응답과 준비/관측 마감을 거부하고, 부분 증적과 정리를 보존한다.
2. 격리 DB에서 대상이 아닌 SELECT, 빠른 성공, 합성 테이블의 제한된 잠금 대기와 서버 timeout을 확인한다. 실제 I/O 대기의 재현을 강제하지 않고 단위 테스트에서 `IO`·`ClientWrite` 및 대기 없음 분류를 검증한다. 고정 주석을 제외한 SQL 본문·읽기 전용 결과·4초/5초 제한과 서버 취소/로컬 제한 구분을 대조한다.
3. 관련 테스트와 `make verify`를 통과시키고 증적이 허용 필드만 갖는지 확인한다. 실제 재현 후에도 잠금·I/O·기타 대기가 관측되지 않으면 원인은 미확정으로 남긴다.
