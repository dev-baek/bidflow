## 목적과 기존 결과의 구분

현재 [집중 부하](../reports/issue-019-focused-load-baseline.md)는 단일 경매 20건·승인 1건이고, [분산 부하](../reports/issue-019-distributed-load-baseline.md)는 6개 경매 2,535건·승인 6건이다. 요청별 중복 원장은 없었지만, 여러 승인 가격이 상승하는 단일 경매의 누적 HTTP 부하를 충분히 관측한 결과는 아니다.

새 실행은 **단일 경매에 최대 20 VU로 총 1,000건**을 제출한다. 1,000개 요청을 한꺼번에 시작하는 실험도, 1,000명의 동시 접속자 실험도 아니다. 기존 #76의 1,000건 어댑터 정합성 테스트, 두 요청씩 10회인 브라우저 실험, 분산 k6 결과와 별도로 보고한다. 상위 프로젝트 사양의 1,000건 동시 HTTP 기준을 이 결과로 완료 처리하지 않는다.

## S. 관측할 사용자 결과

화면과 입찰 규칙은 바꾸지 않는다. 직접 입찰 접수 202와 최종 승인·거절을 구분한다. 낮은 금액이 늦게 처리돼 BID_TOO_LOW로 거절되는 것은 허용하지만, HTTP 성공을 입찰 승인으로 세지 않는다. 새 k6 실행에는 브라우저가 없으므로 공개 화면·개인 WebSocket 전달 P95 2초의 증적으로 사용하지 않는다.

동일 최고가만 반복하지 않고 요청마다 다른 금액과 합성 입찰자를 사용한다. 이 합성 부하는 가격 상승과 원장 순서를 점검하기 위한 것이며 로그인·실제 사용자 행동을 모델링한 테스트는 아니다.

## D. 시험 데이터와 정합성

실행마다 새 runId·상품 UUID·활성 경매 UUID를 사용한다. 시작가 10,000원·초기 version 1·마감까지 30분 이상인 실제 시계의 경매를 만든다. 기존 데이터·Redis 키·볼륨·offset은 지우지 않는다. 상품·경매 삽입만 새 Fixture에 허용하고 검증 조회는 해당 auctionId/runId에 한정한다.

정식 실행은 20 VU가 각각 50번 제출한다. 순번은 `20 * __ITER + (__VU - 1)`로 0~999를 한 번씩 사용한다. 금액은 `10000 + 50000 * (순번 + 1)`이며 최저 60,000원·최고 50,010,000원이다. 현재 BidPriceRules의 최대 최소호가 50,000원보다 작지 않은 간격으로, 높은 순번이 먼저 처리될 때의 정상 거절을 허용한다. 순번을 HTTP 도착 순서나 Kafka 처리 순서로 가정하지 않는다.

각 요청의 멱등 키와 합성 actor는 runId·VU·iteration을 포함한다. 합성 actor는 요청마다 다르며 판매자와도 다르다. 따라서 20 VU는 부하 생성 동시 실행 수이고 합성 입찰자는 총 1,000명이다. 자동입찰과 SELF_BID를 주된 부하로 섞지 않는다.

완료 후 읽기 전용 SQL로 다음을 모두 확인한다.

1. k6 제출 기록의 멱등 키·금액·actor·응답 requestId 집합과 PostgreSQL의 요청 집합이 정확히 일치한다. 집계 건수만 같다고 통과하지 않는다.
2. 1,000개 요청 모두 ACCEPTED 또는 REJECTED이며 미처리 0건이다. 요청마다 원장 1건과 BidAccepted/BidRejected 결과 Outbox 1건이 있고 판정·사유·사용자 연결이 일치한다. bid_request.amount와 bid_ledger.requested_amount는 제출액과 같아야 한다. 승인의 원장/결과 currentPrice는 제출액과 같고, 거절의 currentPrice는 기존 계약대로 null이다. 최신 공개 snapshot 가격과 혼동하지 않는다. 연장 등 다른 이벤트를 결과 중복으로 세지 않는다.
3. 승인 이벤트의 auctionVersion 순으로 가격이 엄격히 증가하고, version은 초기 1에서 승인 건수만큼 연속 증가한다. 같은 시각의 decided_at나 UUID 정렬만으로 순서를 판정하지 않는다. 원장에는 version 컬럼이 있다고 가정하지 않는다.
4. 서로 다른 승인 가격이 2개 이상이어야 한다. 승인·거절 및 사유별 건수는 실제 값으로 보고하고 기대 승인 건수를 임의로 고정하지 않는다. 새 경매/actor 조건에서 BID_TOO_LOW 외 거절이 나오면 원인을 조사하며 정상 성공으로 숨기지 않는다.
5. 최종 ACTIVE 경매는 최고 제출가 50,010,000원이며 마지막 승인 이벤트·원장의 가격과 승자가 일치한다. 최종 version은 1 + 승인 건수다. 마감 5분 미만 조건이 아니므로 endsAt도 그대로여야 한다.
6. 해당 요청의 정산 DLT 유입이 없어야 한다. 그룹 Lag 0만으로 정산 성공을 대체하지 않는다.

낙찰 종료 불변식은 기존 E2E/종료 테스트에 맡긴다. 이번 Fixture는 종료시키거나 기존 사용자 데이터를 정리하지 않는다.

## B. 최소 도구 변경

기존 tests/load/bid-request.js와 실행 경계를 재사용해 별도 `focused-thousand` 시나리오를 추가한다. 기존 focused 20건과 distributed의 입력·금액·페이싱·임계값은 유지한다. 필요하면 요청 계획과 최종 판정만 작은 순수 함수로 분리하고 Node 테스트에서 외부 I/O 없이 검증한다. 새 프레임워크·의존성·도메인 API·DB migration은 추가하지 않는다.

새 시나리오는 per-vu-iterations 20 × 50, maxDuration 120초·gracefulStop 0초, 요청 timeout 5초로 제한한다. 각 반복은 HTTP 응답 뒤 100ms 쉬며 다음 요청을 시작하고, 비동기 최종 정산 완료는 기다리지 않는다. 이를 지속 2분·고정 TPS·포화 부하로 부르지 않는다. [k6 per-VU executor](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/per-vu-iterations/)는 VU별 반복 수를 정하며 시간 제한으로 중단된 반복은 완료가 아니다. 요청 제한은 [HTTP timeout](https://grafana.com/docs/k6/latest/javascript-api/k6-http/params/)으로 별도 지정한다.

HTTP 202라도 status/requestId 파싱이 실패하면 유효 접수가 아니다. 요청별 허용 필드만 외부 결과 디렉터리에 수집하고 원문 응답·토큰·전체 헤더를 저장하지 않는다. 모든 요청을 자동 재시도하지 않으며 전송 실패와 불완전 기록도 보존한다.

로컬 실행 경계는 loopback 또는 Docker의 host.docker.internal:8080만 허용한다. 원격 주소·인증정보 포함 URL·redirect는 거부한다. 기존 범용 runner가 허용하는 원격 주소를 이번 시나리오의 권한으로 사용하지 않는다. Docker에는 스크립트 읽기 전용 mount와 새 결과 디렉터리만 전달하고 저장소 전체를 쓰기 가능하게 mount하지 않는다. 출력은 저장소 밖의 새 경로로 제한하고 기존 파일·symlink 충돌은 서비스 접근 전에 거부한다.

## I. 실행과 관측 경계

정식 실행 전 소스를 커밋하고 SHA·Node/Java/k6·호스트/Docker 자원·서비스 상태·토픽 파티션·프로필·실제 Outbox 간격을 기록한다. 현재 local 기본은 100ms이며, 실행 중 API에 명시적 1,000ms override가 있으면 그대로 실험한 척하지 않는다. 필요 시 소유 프로세스의 인자·jar hash를 확인해 완전 종료 후 실제 시계 local/100ms/INFO로 교체하고, 실험 종료 시 기존 실행 상태로 복원한다. 테스트 Clock·다른 부하·장애 주입과 병행하지 않는다.

처음에는 별도의 새 경매로 2 VU × 5회 smoke를 실행해 10건의 수집·SQL 연결을 확인한다. 금액 순번도 `vus * __ITER + (__VU - 1)`로 계산한다. smoke는 1,000건 본 실행이나 성능 달성으로 합산하지 않는다. 정식 설정은 20 × 50으로 고정하며 결과가 나쁘다고 VU·건수·timeout을 낮춰 같은 기준의 통과로 바꾸지 않는다.

Kafka bid-settlement 세 파티션의 offset/Lag를 전·중·후 수집한다. 실행 중 조회는 한 번씩 순차 실행하고 완료 뒤 3초 대기하며, 매 조회 시작/종료 시각을 기록한다. 실제 관측 간격과 최대 관측 Lag를 보고한다. k6 종료 직후부터 최대 60초 동안 해당 요청의 최종 상태·원장/이벤트 일치와 Lag 0을 확인한다. 첫 완료 조회 시점을 회복 관측 상한으로 기록하고 정확한 회복 시각이라고 부르지 않는다. 부하 시작 전 이미 Lag가 있으면 본 실행을 시작하지 않는다.

호스트 CPU와 BidFlow 컨테이너 메모리/OOM 상태도 실행 구간에 수집한다. 약 1초 간격 호스트 CPU 표본 5개가 연속 90% 이상이거나 OOM/심각한 메모리 압박이 관측되면 부하를 중단하고 성능 결과는 무효로 남긴다. 표본 누락으로 이 조건을 확인할 수 없으면 자원 유효성 미확인으로 기록한다. 낮은 부하의 진단 실행은 별도 runId로만 허용하고 정식 성공을 대신하지 않는다.

AWS 자격증명·Cognito·리소스 명령·배포·네트워크 바인딩 확대는 사용하지 않는다. 복원/중단 실패는 성공 판정보다 우선해 보고한다.

## T. TDD와 완료 판정

구현은 다음 순서로 나눈다. 문서 승인만으로 아래 항목이 완료되는 것은 아니다.

1. 요청 계획 RED: 정식 순번/멱등 키/actor가 1,000개씩 유일하고 금액과 경계가 맞는지, 잘못된 설정·runId를 거부하는지 확인한다. 기존 focused/distributed 계약도 유지한다.
2. 판정 RED: 요청 누락·중복 ID·HTTP 202의 잘못된 본문·원장/이벤트 누락·가격/version 역행·승자 불일치·처리 대기·불허 거절·불완전 자원/Lag 관측을 전체 성공으로 세지 않는다. 총 건수만 맞춘 다른 요청 집합도 실패해야 한다.
3. 최소 GREEN: 가짜 HTTP/SQL/Docker로 timeout·부분 기록·출력 충돌·원격 주소 거부·복원 실패를 검증한 뒤 기존 make verify를 통과시킨다. 서비스가 필요한 실험 자체는 기본 CI에 넣지 않는다.
4. 별도 smoke 후 새 Fixture의 정식 1회 실행을 기록한다. 실패는 보존하고 자동 재실행하지 않는다. 원인 분석이나 코드 수정 뒤의 재실행은 별도 SHA/runId로 구분한다.
5. 구현 PR에는 최신 실제 CI와 실측 증적을 연결한다. full integration check나 브라우저를 추가 실행하지 않았다면 그렇게 명시한다.

접수 API P95 300ms 이하·HTTP 실패율 1% 미만을 성능 기준으로 유지한다. P50/P95/P99는 k6 원본 집계 방식을 명시하며 Node 관측기의 nearest-rank 결과와 합치지 않는다. 완전한 정합성 검증은 1,000건 모두 유효 접수·최종 처리·SQL 대조를 요구하므로 HTTP 실패가 기준 미만이어도 누락 요청이 있으면 전체 성공이 아니다.

성능 기준과 정합성·실행 유효성을 따로 표시한다. P95 초과를 표본 제외나 임계값 변경으로 통과시키지 않는다. DB requested_at→processed_at을 보고한다면 처리 시작 지연으로만 표시하며 DB 커밋 완료·브라우저 전달 지연으로 바꾸지 않는다.

보고서에는 실제 VU·요청/접수/승인/거절/미완료 수, 요청별 대조와 불변식, HTTP 지표, Lag 표본과 조회 상한, 자원 표본·무효 사유, 실행·복원 상태를 남긴다. 원본 민감 로그 대신 허용 필드로 정리한 증적과 재계산 가능한 SQL 결과를 저장한다. #19와 상위 프로젝트의 미검증 범위는 그대로 유지한다.
