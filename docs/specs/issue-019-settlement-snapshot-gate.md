# 정산 조회 전 요청 완결 확인 사양

- 상태: #313 사양 및 #314 구현 병합. [실제 부하 검증](issue-019-settlement-gate-live.md)은 별도 승인 범위다. 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)의 [읽기 전용 진단](../reports/issue-019-scoped-sql-plan-diagnosis.md)에 따른다.

## S. 사용자와 결과 판정

앱의 입찰·정산·화면 동작은 그대로다. 로컬 부하 수집기에서 입찰이 최종 상태에 도달한 뒤에만 전체 SQL을 검증한다. 성공 기준인 원장·이벤트·A/B·회복 및 HTTP 한계는 바꾸지 않는다.

## D. 저비용 준비 확인

읽기 전용 SQL 한 건으로 해당 경매의 요청 전체 수와 `ACCEPTED`/`REJECTED`인 요청 수만 센다. 두 수가 계획 건수와 같아야 조회 준비 완료다. 상태 수는 정합성 증거가 아니며 다른 경매나 부분 완료·초과 건수·누락·잘못된 응답으로는 진행하지 않는다. 기존 전체 SQL의 요청별 원장·결과·승자·version·마감 대조와 A/B 이벤트/DOM 대조를 유지한다.

## B. 수집 순서

기존 수집기의 회복 단계에서 먼저 새 Kafka Lag를 확인하고 세 파티션 모두 0일 때만 준비 확인을 호출한다. 데이터가 덜 끝났으면 기존 마감 안에서만 관측하고, 전체 SQL은 준비 완료 뒤 **최대 한 번** 호출한다. 전체 SQL이 성공한 경우에도 이후 Lag·DLT 및 기존 판정까지 확인해야 성공이다. Lag 0·건수·부분 기록만으로 통과 처리하지 않는다.

준비를 기다리다 마감이면 전체 SQL을 호출하지 않고 미완료를 기록한다. 준비 조회 오류, 전체 SQL 실패, 후속 Lag/정합성 불일치에서는 자동 재호출하지 않는다. 기존 부하 중 관측과 HTTP/SQL/명령 판정은 유지하고 readiness용 조회와 결과는 별도 허용 필드로 기록한다. 기존 전체 SQL·스키마·인덱스·타임아웃은 바꾸지 않는다.

## I. 실행 제한

기존 4초 statement·5초 프로세스와 부하 종료 뒤 60초 회복/관측 예산 안에서 실행한다. 준비 대기나 SQL에 새 마감을 부여하지 않는다. 실제 새 부하·API 재시작·AWS는 이 구현 승인에 포함되지 않는다.

## T. 구현 전 회귀 테스트

1. 가짜 Lag/DB/시계로 Lag 양수, Lag 0이지만 요청 미완료, 정확히 완료된 상태에서 전체 SQL 호출 횟수 0/0/1을 검증한다. 잘못된 건수, 마감 초과·준비 실패·SQL 취소가 전체 성공을 만들지 않아야 한다.
2. Lag가 뒤늦게 올라가거나 원장/이벤트가 불일치할 때 전체 SQL을 반복하지 않고 실패하며, 부분 frame/DOM과 정리/복원 정보가 남는지 확인한다.
3. 기존 스크립트·가짜 I/O·`make verify`를 통과시킨다. 이번 사양을 병합해도 과거 본 실행의 취소 판정을 바꾸거나 새 실행을 허용하지 않는다.

## 구현 및 검증 결과

- 수집기가 회복 단계의 각 새 Lag 표본을 확인한 뒤, 세 파티션이 0일 때만 경매 범위의 완료 건수를 조회한다. 증적에는 `SETTLEMENT_READINESS` 명령과 `readinessChecks`의 허용된 시각·건수만 기록한다. 기존 전체 SQL과 성공 판정은 유지한다.
- 같은 회복 마감에 기존 명령 제한을 수용할 여유가 없으면 해당 명령을 시작하지 않는다. 명령이 늦게 끝나도 후속 SQL을 시작하지 않는다. 전체 조회 또는 후속 확인이 실패하면 같은 전체 SQL을 반복하지 않고 이미 확보된 화면 및 복원 기록을 남긴다.
- 가짜 시계와 I/O에서 적체·부분 완료·다른 경매·초과 건수·조회 오류·마감, 본 SQL 실패와 이후 Lag/정합성 불일치를 검증했다. 결과가 없는 상태와 준비된 상태의 전체 SQL 호출 횟수를 구분했다.
- 기존 #312의 smoke와 본 실행 경매만 새 건수 SQL로 읽었다. 각 10/10·1,000/1,000의 전체/완료 수와 경매 범위가 일치했다. 이는 지금의 저장 상태이며, 당시 부하에서 준비 확인이나 전체 SQL이 통과할 것이라는 증거가 아니다. 기존 부하 실행·API 재시작·AWS 작업은 하지 않았다.
