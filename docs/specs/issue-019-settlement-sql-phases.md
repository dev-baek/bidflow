# 정산 검증 SELECT 비용 분리 진단 사양

- 상태: 검토 대기. 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)의 후속 진단이다. 이 PR은 사양만 추가한다.
- 근거: [#316 서버 취소](../reports/issue-019-settlement-gate-live.md), [#320 인덱스 비교](../reports/issue-019-settlement-outbox-comparison.md), [#324 실제 부하 관측](../reports/issue-019-settlement-wait-live.md).

#316과 #324에서는 Kafka Lag 0과 입찰 처리 상태 1,000건을 확인했지만, 검증용 정산 SELECT가 서버의 4초 제한에 걸려 같은 실행의 원장·A/B 화면을 대조하지 못했다. #324의 활성 표본 39개 중 I/O는 1개였고 나머지는 표시된 대기가 없었다. I/O가 원인이었다거나 나머지 시간을 CPU가 모두 사용했다고 볼 수 없다. #320의 인덱스 후보는 채택 기준에 미달했으므로 다시 적용하지 않는다.

현재 조회는 요청·원장·정산 이벤트를 경매별로 읽고, 요청별로 그룹화한 뒤 중첩 JSONB 하나를 만든다. 실행 계획과 전체 psql 호출 시간만 비교하면 **서버에서 JSONB를 구성하는 비용, 반환값을 텍스트로 변환하는 비용, 호출 전체 시간**이 섞인다. 같은 SELECT를 유지하면서 이 세 관측을 구분한다.

## S. 화면과 완료 판정

화면 및 입찰 동작은 변경하지 않는다. 이전 본 실행의 원장·A/B 화면 검증은 미완료로 남긴다. 이번 진단의 완료는 합성 DB에서 측정 방법을 검증했다는 뜻이며, 실제 정산이나 종합 성능 목표 통과가 아니다.

## D. 합성 데이터와 결과 계약

#320과 같은 두 규모를 사용한다. 고정 시드로 대상 경매에 요청·원장·정산 이벤트 각 1,000건을 만들고, 무관한 Outbox 이벤트를 2,000개 또는 100,000개 추가한다. 스키마와 통계 준비 절차는 두 규모에서 동일하게 유지한다. 실제 경매·입찰 자료를 복사하지 않는다.

일반 호출의 JSON은 기존 판정기와 경매 상태·전체 카운트·요청별 원장 및 이벤트로 검증한다. 배열 순서만 정규화할 수 있고 중복 제거는 하지 않는다. `EXPLAIN` 출력은 계획 자료이며 원장 대조 결과로 세지 않는다.

## B. 같은 SELECT의 세 관측

[정산 조회 모듈](../../scripts/concurrent-browser-sql.mjs)의 전체 경매 SELECT를 재사용한다. 별도 문자열 복제, 결과를 줄인 조회, 플래너 강제 설정은 사용하지 않는다. 정산 명령과 예산은 변경하지 않는다.

| 관측 | 기록 | 한계 |
|---|---|---|
| `EXPLAIN (ANALYZE, BUFFERS, SERIALIZE NONE, FORMAT JSON)` | 계획/실행 시간, Outbox 스캔 및 그룹화·조인·집계 노드의 행·loops, 공유/임시 블록 | SELECT 내부 JSONB 생성은 실행에 포함된다. 클라이언트 전송용 텍스트 변환은 제외된다. 노드 시간과 블록은 상하위 노드 간에 중복될 수 있다. |
| `EXPLAIN (ANALYZE, BUFFERS, SERIALIZE TEXT, FORMAT JSON)` | 위 항목과 서버 텍스트 변환 시간 및 출력 크기(kB) | 결과 JSON 본문을 psql로 보내는 시간은 포함하지 않는다. 일반 호출의 stdout 바이트와 같은 지표가 아니다. |
| 기존 psql 일반 호출 | 전체 경과, 출력 바이트와 결과 검증, 실패 종류 | 프로세스 시작·연결·쿼리·출력 비용을 포함한다. 계획 실행 시간과의 차를 순수 전송 시간으로 해석하지 않는다. |

[PostgreSQL 17의 EXPLAIN 계약](https://www.postgresql.org/docs/17/sql-explain.html)을 따른다. `SERIALIZE TEXT`는 실제 변환을 수행하므로 타이밍을 끄지 않는다. 실행 시간에 이미 포함된 변환 시간을 다시 더하지 않는다. 계획 계측 자체에 오버헤드가 있으므로 세 관측의 시간 합이나 차로 원래 4초를 설명하지 않는다. 추가로 I/O 타이밍을 설정하지 않는다.

## I. 격리와 실행 제한

사양 병합 후 PostgreSQL 17.5 별도 컨테이너 한 개에서만 실행한다. 네트워크·공개 포트·영구 볼륨 없이 구성하고, 기존 Compose·DB·API·Kafka에는 연결하지 않는다. 데이터 준비 뒤 읽기 전용 트랜잭션, 서버 4초, psql 호출 5초를 유지한다. PostgreSQL 버전·격리 조건·첫 일반 호출의 결과 계약이 확인되지 않으면 측정하지 않는다.

규모마다 일반 호출로 확인한 뒤 세 관측의 순서를 순환해 **각 3회**, 총 9개 측정 표본만 수집한다. 캐시를 강제로 비우지 않는다. 시간 초과·출력 오류가 나면 실패 구간을 남기고 중단하며 자동 재시도하지 않는다. 원본 계획과 JSON은 저장소 밖에 두고, 집계·출력 해시·고정 실패 코드와 정리 결과만 커밋한다. 컨테이너와 임시 파일은 종료 시 제거한다.

## T. 검증과 종료 기준

1. 실패 테스트를 먼저 작성한다. 세 경로가 같은 SELECT를 사용하고, `SERIALIZE TEXT`에서 변환 필드가 누락되거나 일반 결과의 행이 누락·중복되면 성공 판정을 내리지 않는지 검증한다. 서버 취소, 로컬 마감, 출력 오류는 구분한다.
2. 두 규모의 계획 구조·블록·변환량·호출 분포를 각각 보고한다. 여러 표본이 같은 구간을 가리킬 때만 다음 개선 후보를 제안하며, 재현되지 않거나 근거가 부족하면 원인은 미확정으로 유지한다.
3. 이 사양은 인덱스·마이그레이션·제한 변경, 실제 입찰 부하 재실행, 기존 DB 재조회, AWS 실행을 승인하지 않는다.
