# 입찰 접수 서버 구간 계측 사양

- 상태: 검토 대기. 기존 [#19](https://github.com/dev-baek/bidflow/issues/19)의 [요청별 진단](../reports/issue-019-smoke-http-diagnosis.md)을 근거로 한다.

## S. 사용자 동작

입찰 화면, 202 접수와 비동기 정산 계약은 바꾸지 않는다. 목적은 HTTP 전체 실측과 서버의 접수 처리 구간을 요청별로 대조하는 것이다. 브라우저 화면 수렴이나 Kafka 최종 처리 시간을 HTTP에 합치지 않는다.

## D. 관측 계약

동일한 부하 요청의 k6 duration과 서버 관측을 연결하기 위해 기존 응답의 `X-Correlation-Id`와 `bidRequestId`를 사용한다. 상관 ID와 요청 ID는 허용된 형식만 보존한다. 재전송은 요청 ID가 같아도 HTTP 호출별 상관 ID를 구분하고, 모호·중복·누락 연결은 미완료로 기록한다. 새 DB 컬럼·테이블·인덱스는 추가하지 않는다.

## B. 최소 계측

| 관측 | 경계 |
|---|---|
| HTTP 서버 구간 | 기존 요청 필터에 진입해 필터 체인이 반환하거나 예외로 종료하기까지. 소켓 전송 완료·필터 진입 전 지연은 포함하지 않는다. |
| 접수 서비스 구간 | 컨트롤러가 `service.receive`를 호출해 반환 또는 예외를 받은 구간. 멱등 조회와 저장 경계가 함께 포함된다. |
| 클라이언트 구간 | 기존 k6 duration과 그 HTTP 응답의 허용된 상관 ID. 서버 단조 시계와 타임스탬프를 직접 빼지 않는다. |

서버에서는 각 경계 시작/끝 차이를 단조 시계로 기록한다. 기존 접수 로그로 정상 요청을 연결하고 실패는 고정 결과 코드로 구분한다. 동일한 요청에 대해 올바르게 중첩된 측정값만 비교한다. 이번 변경은 DB pool과 SQL의 원인을 추측해 세부 계측을 미리 늘리지 않는다. 서버 구간이 확보된 뒤 더 좁은 경계가 필요한지를 결정한다.

## I. 로컬 제한

기본 비활성인 local 검증 전용 설정으로, 지정된 입찰 POST만 계측한다. 기존 상관 ID 전파, 응답·예외, MDC 정리 및 지표의 태그 계약은 유지한다. URL 원문·헤더 전체·토큰·actor·멱등 키·본문·SQL은 계측 로그에 넣지 않는다. CloudWatch나 운영 설정을 추가하지 않는다.

## T. TDD 및 승인 경계

기존 필터·컨트롤러 테스트에서 가짜 단조 시계로 경계/순서를 검사한다. 비활성/다른 경로에서 추가 기록 없음, 202와 실패 응답/예외 보존, MDC 정리, 중복·누락 ID와 민감 필드 거부, 기존 수집기 판정 불변을 확인한다. `make verify`를 통과한 뒤 구현과 테스트 결과를 보고한다. 병합은 계측 구현·테스트 승인 범위이며, 새 입찰 부하·API 재시작·AWS 실행은 별도 승인이다.
