# 정산 조회 전 완료 확인의 실제 부하 검증 결과

[#315 승인](../specs/issue-019-settlement-gate-live.md)으로 새 경매에서 10건 smoke를 통과한 뒤, 별도 경매에서 누적 1,000건을 한 번 실행했다. **1,000건이 모두 접수됐고, Kafka Lag 0과 요청 1,000건 완료를 확인한 뒤 정산 SQL을 정확히 한 번 호출했다. 정산 SQL이 다시 4초 제한에 걸려 전체 검증은 통과하지 못했다.** 완료 확인은 계획대로 동작했지만, 그것만으로 SQL 시간 초과는 해소되지 않았다.

## 실행별 결과

2026년 11월 23일 19:01:48~19:03:07 JST, 소스 `3173db042dfbdf0293d8d92f57a0beaab2359715`의 깨끗한 별도 worktree에서 실행했다. 사전 `make verify`는 Java 단위 테스트·Node 134개·Vitest 71개·빌드를 통과했다. 검증 API는 local/system Clock/100ms/INFO/INGRESS_TIMING, 브라우저와 API는 loopback만 사용했다.

| 항목 | smoke 2 VU × 5회 | 본 실행 20 VU × 50회 |
|---|---|---|
| HTTP | 10/10 접수, 오류 0%, P50/P95/P99 98.09/132.36/137.01ms | 1,000/1,000 접수, 오류 0%, 28.61/270.50/507.32ms |
| 요청별 계측 | 응답·접수·타이밍 10/10 연결 | 1,000/1,000 연결, 중복·누락·파싱 오류 없음 |
| 정산 SQL | 요청·원장·결과 각각 10개, 승인 5·거절 5 | 1회 호출, 4초 statement timeout으로 취소 |
| A/B 화면 | 각 브라우저의 510,000원/v6 frame과 화면이 DB 최종 승인과 일치 | 두 화면에서 같은 50,010,000원/v165 이벤트를 관측. SQL 대조 미완료 |
| 후속 관측 | 정합성 및 후속 Lag 0은 부하 종료 +7.056초, DLT 불변은 +8.286초에 확인 | SQL 실패로 후속 Lag·DLT·최종 자원 판정 미실행 |
| 실행기 | exit 0, `valid=true`, `browserObservationValid=true`, `fullVerified=false` (smoke) | k6 exit 0, 실행기 exit 1, `valid=false`, `fullVerified=false` |

본 실행의 HTTP 수치는 P95 < 300ms·오류율 < 1%를 충족한다. 300ms 이상 요청은 34건이었고, 서버 필터와 접수 서비스의 nearest-rank P95는 각각 250.53ms와 245.82ms였다. SQL 실패로 실행기는 전체 판정까지 도달하지 않았다. 이 수치는 20 VU의 누적 제출 결과이며, 1,000건 전체 동시 요청이나 운영 환경의 성능이 아니다.

## 완료 확인과 정산 SQL 호출 순서

아래 시각은 실행기 단조 시계의 **부하 종료 기준**이다. 부하 시작 전 경매 생성용 SQL은 정산 호출에 포함하지 않았다.

| 순서 | smoke | 본 실행 |
|---|---|---|
| 새 Lag 표본 완료 | +5.369초, 세 파티션 [0, 0, 0] | +9.358초, 세 파티션 [0, 0, 0] |
| 경매 범위 준비 확인 완료 | +5.545초, 전체/완료 10/10 | +9.552초, 전체/완료 1,000/1,000 |
| 전체 정산 SQL | +5.545초에 시작, 196.25ms 뒤 성공 | +9.553초에 시작, 4,176.98ms 뒤 취소 |
| 후속 확인 | 새 Lag [0, 0, 0], DLT [0, 0, 0] 유지 | SQL 실패로 시행하지 않음 |

본 실행의 명령 추적 #40 → #41 → #42에서 이 순서를 확인했다. #42는 5초 클라이언트 프로세스 제한 전에 exit 1 및 `SQL_QUERY_CANCELED`로 종료됐다. 같은 시간의 PostgreSQL 로그(19:02:58.071 JST)에서도 statement timeout을 확인했다. Lag와 완료 수를 확인하고도 취소가 재현됐지만, SQL 내부에서 시간이 소요된 원인까지 확정하지는 않았다.

A/B의 동일 50,010,000원/v165 frame과 이후 DOM 확인은 부하 종료 약 8.18초 뒤에 남았다. DB 스냅샷이 없어 해당 eventId를 원장의 최종 승인과 일치한다고 판정하지 않았다.

## 복원과 다음 검증

검증 API·Vite·부하·브라우저를 종료하고 원래 1,000ms API를 복원했다. 기존 인자·jar 해시·loopback 포트와 readiness `UP`을 확인했다. 컨테이너 5개의 ID와 healthy 상태는 그대로였다. [구조화 증적](evidence/issue-019-settlement-gate-live.json)에 순서·요청별 계측 집계·화면·복원을 남겼고 원본은 보호된 로컬 경로에만 보존했다.

재시도·사후 DB 조회·임계값 변경·AWS 작업은 하지 않았다. #302/#306/#312 판정도 유지한다. 다음 단계는 기존 [읽기 전용 진단](issue-019-scoped-sql-plan-diagnosis.md)과 이 결과를 바탕으로, 건별 원장과 최종 이벤트 대조를 유지하면서 조회 비용을 낮출 사양을 [#19](https://github.com/dev-baek/bidflow/issues/19)에 먼저 정하는 것이다.
