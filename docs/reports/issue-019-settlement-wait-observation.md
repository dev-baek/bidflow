# 정산 SQL 대기 관측 구현과 격리 검증

정산 SELECT의 대기를 기록하는 로컬 옵션 `--settlement-waits`를 추가했다. 기본 부하 실행은 바뀌지 않는다. [#321 사양](../specs/issue-019-settlement-wait-observation.md)에 따라 정산 SQL 실행 구간에 속한 표본 중, 이 SELECT를 실행 중인 세션만 대기 유형으로 분류한다.

## 수집 범위

새 Lag 0과 입찰 완료 수를 확인한 뒤 기존 정산 SQL을 한 번 호출한다. 진단 옵션은 별도 읽기 전용 psql 세션에서 100ms 이상 간격으로 최대 50개 표본을 읽는다. 태그와 PID가 바뀌거나 대상이 중복되면 진단을 무효로 남긴다. 원문 SQL, PID, 사용자 데이터는 증적에 포함하지 않는다.

기존 4초 SQL과 5초 프로세스 제한, 60초 회복 마감, 원장·화면 판정은 그대로다. 관측이 실패해도 원래 SQL 결과를 보존하고 재호출하지 않는다. 대기 값이 보이지 않는 표본은 CPU 사용 시간으로 세지 않는다.

## 격리 PostgreSQL 결과

2026년 11월 24일 00:37:04~00:37:16 JST, 별도 PostgreSQL 17.5에서 합성 경매와 요청·원장·이벤트를 사용했다. 기존 DB나 Kafka는 연결하지 않았다.

| 사례 | 결과 |
|---|---|
| 빠른 정산 SELECT | 기본 호출과 결과가 같았다. 활성 표본이 없어 `NO_ACTIVE_SAMPLES`로 기록했다. |
| 같은 세션의 다른 SELECT와 다른 태그의 표시된 SELECT | 다른 문장 7표본을 제외했다. 활성 정산 표본은 0개였다. |
| 합성 테이블 잠금 해제 | `LOCK` 8표본을 관측했다. 조회는 성공했고 기본 호출과 결과가 같았다. |
| 합성 테이블 잠금을 유지 | `LOCK` 39표본을 관측했다. 서버가 SQL을 취소했고 `STATEMENT_TIMEOUT`으로 분류했다. psql 호출 경과는 4,167.96ms였다. |
| 로컬 프로세스 제한 | 합성 자식 프로세스의 짧은 제한으로 `SQL_PROCESS_TIMEOUT`을 확인했다. 실제 정산 호출의 5초 인자는 그대로였다. |

첫 격리 실행에서는 서버 취소 전에 `LOCK` 26표본이 남았지만 관측기가 중간에 오류로 종료됐다. 타이머가 먼저 깨어날 때에도 단조 시계로 다음 표본 시작 시각을 다시 확인하도록 보강했다. 위 재검증에서는 관측 오류 없이 39표본을 모았다. 첫 실행의 관측 오류 원인은 확정하지 않았다.

## 정리와 남은 범위

각 사례 후 대상·관측 세션이 남지 않았고 실험 컨테이너를 제거했다. 기존 서비스 5개의 상태와 API readiness UP을 확인했다. [구조화 증적](evidence/issue-019-settlement-wait-observation.json)에 명령 경과, 표본, 분류와 정리를 남겼다.

이 결과는 합성 잠금을 구분할 수 있음을 보여준다. 실제 I/O 대기는 강제 재현하지 않았으며, [#316의 취소 원인](issue-019-settlement-gate-live.md)도 확정하지 않는다. 새 10/1,000건 입찰, 기존 DB 변경, AWS 작업은 하지 않았다. 실제 부하 재검증은 별도 승인 범위다.
