# 정산 Outbox 부분 인덱스 최종 비교

**기존 스키마를 유지한다.** 확장 데이터에서 부분 인덱스는 Outbox 공유 블록 접근을 4,810개에서 905개로 줄였다. 그러나 전체 조회 호출 중앙값은 278.59ms에서 232.46ms로 16.56% 개선돼, [사양](../specs/issue-019-settlement-outbox-index.md)의 **20%와 10ms를 모두 충족**해야 하는 기준에는 못 미쳤다. 쓰기 시간은 허용 범위였지만 WAL은 늘었다.

## 실험 범위와 결과 동등성

2026년 11월 24일 00:11:21~00:12:06 JST, 소스 `8efe909d2cea36f6da1fd65bed3785a05dc66fa9`에서 실행했다. 별도 PostgreSQL 17.5 컨테이너는 네트워크·공개 포트·영구 볼륨 없이 임시 파일시스템만 사용했다. 이 컨테이너에서 [호출 점검](issue-019-psql-call-probe.md)과 같은 4종을 먼저 실행해 24/24를 통과했다. 가장 느린 점검은 1,277.32ms였다. 그 뒤에만 합성 데이터를 넣었다.

두 규모 모두 대상 경매에 요청·원장·결과 각 1,000건을 넣고, 무관한 이벤트를 각각 2,000개와 100,000개 추가했다. 동일 데이터를 복제한 뒤 후보군에만 부분 인덱스 한 개를 만들었다. 양쪽의 전체 조회, 같은 경매의 두 요청 상세, 별도 2건 경매, 빈 경매, 부분 완료 결과 5종이 각 규모에서 일치했다. 배열 순서만 맞춰 비교했고, 중복 제거 없이 기존 판정기와 출력 해시로 확인했다. 두 요청 상세의 전체 카운트는 여전히 1,000이었다.

## 읽기 비교

각 규모에서 준비 조회 후 기존→후보와 후보→기존 순서를 번갈아 6쌍씩 측정했다. 4초 SQL·5초 프로세스 제한 안에 모든 표본이 완료됐다. 프로세스 시간은 Docker 실행부터 psql 출력 종료까지이며, 전체 조회 응답은 양쪽 모두 706,757B였다.

| 규모 | Outbox 공유 블록 (기존 → 후보) | 전체 조회 중앙값 (기존 → 후보) | 변화 | 후보 크기 |
|---|---:|---:|---:|---:|
| 작은 사례 | 147 → 149 | 224.65 → 241.91ms | 악화 7.68% | 48KiB |
| 확장 사례 | 4,810 → 905 | 278.59 → 232.46ms | 개선 16.56% | 384KiB |

기존 쿼리는 두 규모에서 순차 스캔을 했고 후보는 설정을 강제하지 않아도 비트맵 스캔을 사용했다. 확장 사례에서 블록 접근은 81.19% 줄고 전체 호출은 46.13ms 빨라졌다. 블록 절반과 10ms 기준은 충족했지만 20% 기준은 미달했다. 작은 사례의 중앙값 증가는 17.26ms(7.68%)로 허용 범위 내였다.

별도 EXPLAIN 1회에서 확장 사례의 서버 실행 시간은 84.76 → 162.54ms였다. 이는 일반 호출 6쌍의 중앙값과 다른 측정이다. 접근 블록 감소만으로 서버 실행 시간까지 빨라졌다고 결론내리지 않는다.

## 쓰기 비교

읽기 비교 뒤, 같은 이벤트 250건 삽입과 발행 시각 표시를 양쪽에서 6쌍씩 비교했다. 매번 250건이 표시됐는지 확인한 뒤 트랜잭션을 롤백했다. 아래는 PostgreSQL EXPLAIN의 문장 실행 시간과 WAL 기록 바이트 각각의 중앙값이다. 운영 커밋·디스크 flush 지연을 측정한 결과는 아니다.

| 규모 | 삽입 시간 | 발행 표시 시간 | 삽입 WAL | 발행 표시 WAL |
|---|---:|---:|---:|---:|
| 작은 사례 | 4.71 → 8.14ms | 4.80 → 6.62ms | 133,633 → 155,097B | 133,483.5 → 152,316.5B |
| 확장 사례 | 6.98 → 6.59ms | 18.85 → 20.73ms | 133,380 → 151,878B | 134,382 → 153,140B |

두 규모의 쓰기 시간은 사양의 허용 범위를 넘지 않았다. 확장 사례의 WAL은 삽입과 발행 표시에서 각각 약 13.9%, 14.0% 늘었다. 합성 환경에서 확인한 WAL 양을 운영 저장 비용으로 환산하지 않았다.

## 판단과 정리

격리 비교는 완료했지만 채택 기준은 미달했다. 별도 [#318의 호출 시간 초과](issue-019-settlement-outbox-index.md)나 [#316의 서버 SQL 취소](issue-019-settlement-gate-live.md)를 소급해 바꾸지 않는다. 이 인덱스는 적용하지 않는다. #19에서 남은 질문은 실제 정산 SQL의 서버 시간 중 쿼리 연산과 잠금·I/O 대기가 각각 얼마나 차지했는지다.

실험 컨테이너와 임시 파일시스템은 제거됐다. 기존 로컬 서비스 5개의 ID·시작 시각·healthy 상태와 API readiness UP을 확인했다. [구조화 증적](evidence/issue-019-settlement-outbox-comparison.json)에 호출 점검, 표본, 계획, 출력 해시 및 판정을 남겼다. 기존 DB·애플리케이션·조회 제한은 바꾸지 않았고, 새 입찰 부하 및 AWS 작업은 하지 않았다.
