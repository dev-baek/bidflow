# 접수 계측을 포함한 천 건 부하 검증 결과

[#311 승인](../specs/issue-019-ingress-full-verification.md)으로 새 10건 smoke와 별도 경매의 1,000건 본 실행을 각각 한 번 수행했다. **본 실행에서 1,000건 모두 접수됐고 서버 계측도 1,000/1,000 연결됐다. 정산 조회가 4초 제한을 넘겨 전체 검증은 미완료다.** 두 화면의 기록은 보존했지만 SQL 대조를 통과한 것으로 세지 않았다.

## 실행과 단계 판정

2026년 11월 23일 18:34:39~18:35:46 JST, 소스 `a57674c82a67108f88f61d8d67fd1a1cdf2dda0c`의 깨끗한 별도 worktree에서 수행했다. 사전 `make verify`(Java 단위·Node 130개·Vitest 71개·빌드), JVM·브라우저·Docker 상태를 확인했다. 두 실행 모두 local/system Clock/100ms/INFO/INGRESS_TIMING과 기존 제한을 유지했다.

| 항목 | smoke 2 VU × 5회 | 본 실행 20 VU × 50회 |
|---|---|---|
| HTTP | 10/10 접수, 오류 0%, P50/P95/P99 61.41/233.23/233.33ms | 1,000/1,000 접수, 오류 0%, 29.61/178.09/470.69ms |
| 계측 | 요청별 응답·접수·타이밍 10/10 연결 | 1,000/1,000 연결, 고유 UUID 1,000개, 중복·누락·파싱 오류 0 |
| SQL과 화면 | 요청·원장·결과 각 10개(승인 9·거절 1), 510,000원/v10과 A/B 일치 | 정산 SQL 취소. 두 화면의 최종가 기록은 남았으나 SQL 대조 미완료 |
| 운영 관측 | 자원·명령 30개·Lag 0 및 DLT 불변 확인 | 명령 38개 중 정산 SQL 1개 실패. 마지막 Lag 표본 [0, 204, 0], 회복·DLT 사후·최종 자원 판정 미완료 |
| 실행기 | exit 0, `valid=true`, `browserObservationValid=true` | k6 exit 0과 별개로 실행기 exit 1, `valid=false`, `fullVerified=false` |

smoke의 모든 조건과 단계 정리를 확인한 뒤에만 본 실행을 시작했다. 본 실행의 HTTP 수치만 보면 임계값을 충족했으나, 정산 조회 오류로 실행기는 종합 성능·정합성 판정까지 도달하지 않았다. 300ms 이상 요청은 19개였다.

## SQL 실패와 보존한 화면

본 실행의 정산 `SCOPED_SQL`은 약 4.189초 뒤 exit 1, 진단 코드 `SQL_QUERY_CANCELED`로 끝났다. 해당 시간대 PostgreSQL 로그(18:35:38.816 JST)도 statement timeout 취소를 확인했다. 5초 클라이언트 프로세스 제한과 구분하며, 4초를 초과한 내부 원인은 확정하지 않았다.

A/B는 각각 118개 공개 frame을 받았다. 같은 도메인 eventId의 50,010,000원/v118 frame을 두 브라우저가 수신한 뒤, 두 화면에서 같은 가격을 확인한 기록이 각각 부하 종료 약 6.35초 뒤에 남았다. 이는 새 부분 DOM 보존의 실제 증거다. SQL이 없으므로 이 eventId를 DB의 최종 승인 이벤트나 원장 조건과 일치한다고 판정하지 않는다.

## 서버 접수 계측의 범위

본 실행에서 서버 필터·접수 서비스의 nearest-rank P95는 각각 163.15ms와 160.12ms였다. 가장 느린 요청 하나의 k6 HTTP/서버 필터/접수 서비스는 737.90/661.10/659.26ms로, 해당 서버 표본에서는 서비스 구간이 필터 시간의 대부분을 차지했다. 접수 서비스에는 멱등 조회와 저장이 함께 들어가므로 개별 SQL·락·커넥션 대기나 커밋으로 분리할 수 없다. 서로 다른 요청/시계의 백분위를 빼서 해석하지 않았다.

## 복원과 남은 작업

기존 1,000ms API를 PID 54954로 복원하고 기존 인자·jar hash·listen·readiness를 확인했다. 소유 검증 API·Vite·브라우저·부하를 정리했으며 BidFlow 컨테이너 5개의 ID와 healthy 상태가 그대로였다.

[구조화 증적](evidence/issue-019-ingress-full-verification.json)에 단계별 결과와 선택 표본·부분 화면·복원을 남겼다. 요청별 전체 계측과 원본 로그는 보호된 로컬 경로에만 보존했다. 재시도·추가 DB 조회·기준 변경·AWS는 하지 않았다. #302·#306의 기록도 유지한다. 다음에는 반복된 정산 조회의 비용을 읽기 전용 근거로 좁힌 뒤, SQL 변경이나 추가 실행이 필요한지 검토한다.
