# [Issue #19] Outbox 1,000ms → 100ms → 1,000ms 실측

## 결론

이번 로컬 순차 입찰에서는 100ms 조건 B의 **기본 화면 관측 P95가 431.20ms**로 기존 2초 기준을 통과했다. 1,000ms인 A1/A2는 각각 2,924.07ms/2,936.64ms로 실패했다. B의 명령·결과 DB INSERT→조회 age P95도 두 기준 회차보다 모두 낮았다.

대신 유휴 poll 완료 빈도는 약 1회/초에서 9.43회/초로 늘고 PostgreSQL CPU 중앙값도 0.21%에서 0.985%로 증가했다. **지연 개선과 빈 조회 비용을 함께 확인한 단일 로컬 A-B-A 결과**이며 운영 SLO나 기본값 채택 결정은 아니다. 종료 후 `local / 1,000ms / DEBUG off`로 복원했다.

## 환경과 절차

- 사양: [간격 대조 실험](../specs/issue-019-outbox-delay-experiment.md), 구현: [DEBUG 계측·수집 연결](issue-019-outbox-delay-implementation.md).
- 기준 소스: `b85b671dbc71306d243303746cbe4423117f02c3`(#267 병합). 채택 회차 실행: 2026-11-19 07:07–07:14 UTC.
- Java 21.0.7, Node 24.18.0, Chromium 145.0.7632.6, 기존 Vite와 Docker 5개 서비스. 컨테이너 식별자·이미지·실행 인자·시각은 원본 metadata에 있다.
- 세 조건 모두 같은 bootJar를 `java -jar`로 실행했다. 시작/끝 SHA-256 일치를 확인했다. 기존 Gradle bootRun 회차와 JVM 실행 방식이 다르므로 이전 보고서와의 차이를 간격 변경 효과로 계산하지 않는다.
- API 프로세스 하나를 `local,e2e`로 실행하고 각 조건에서 새 경매 20건으로 워밍업했다. 대기 Outbox 0건을 확인한 후 유휴 60초, 별도 경매 20건을 측정했다. 워밍업 60건은 본측정 백분위에 합치지 않았다.
- API·CPU·E2E 창 표시를 동시에 기존 수집기 stdin에 전달했다. E2E가 출력한 첫 클릭/마지막 결과 표시의 **수신 시각**으로 입찰 관측 창을 정했다. 명시한 창 밖의 준비/워밍업은 지연·비용 집계에서 제외했다.
- 각 회차의 입찰 종료 후 읽기 전용 SQL로 경매·원장·Outbox 연결을 확인했다. SQL 수집 시각은 원본에 남겼고 측정 창 안의 CPU 부하로 넣지 않았다.

원본: [채택한 A1/B/A2 전체 증적](evidence/issue-019-outbox-delay-aba.json) · [중단한 선행 시도](evidence/issue-019-outbox-delay-discarded.json). API 원문 payload·Token·전체 로그·trace·스크린샷은 커밋하지 않았다. event 로그는 기존 허용 필드만 보존했다.

## 브라우저 — 각 조건 완료 20건, 미완료 0건

아래 단위는 모두 ms다. 기본 화면 완료 조건·기본 polling·동시 25ms 보조 관측·2초 임계값을 유지했다.

| 조건 | 기본 P50 | 기본 P95 | 기본 P99 | 개인 frame P95 | 보조 화면 P95 |
|---|---:|---:|---:|---:|---:|
| A1 / 1,000ms | 1,924.05 | **2,924.07** | 2,940.94 | 1,971.52 | 1,982.82 |
| B / 100ms | 418.16 | **431.20** | 439.23 | 272.08 | 291.29 |
| A2 / 1,000ms | 1,925.64 | **2,936.64** | 2,940.30 | 2,054.27 | 2,076.29 |

A1/A2의 지연 E2E는 기본 P95 단언에서 exit code 1, B는 exit code 0이었다. 두 실패 회차도 20건 수집·최종 경매 단언은 완료했다. 세 수집기의 exit code는 모두 0이다. 수집기의 `valid`와 E2E의 2초 기준 통과를 혼동하지 않는다.

A2에서 다시 약 2.94초로 돌아와, 이번 조건에서는 실행 순서만으로 B의 낮은 지연을 설명하기 어렵다. 다만 통계적 유의성이나 장기간 재현성을 검증한 것은 아니다. 화면 관측에는 Playwright 대기가 포함되며 정확한 paint 시각이 아니다. 기본 관측을 보조 관측으로 바꾸거나 60건을 합쳐 기준을 판정하지 않았다.

## Outbox — 종류별 각 20개, P95

| 지표(ms) | A1 | B | A2 |
|---|---:|---:|---:|
| 명령 INSERT→조회 age | 894 | 92 | 953 |
| 결과 INSERT→조회 age | 1,002 | 104 | 1,005 |
| 명령 조회 반환→발행 호출 | 0.003792 | 0.001083 | 0.003750 |
| 결과 조회 반환→발행 호출 | 0.004750 | 0.001584 | 0.004792 |
| 명령 직렬화/전송→ack | 6.660417 | 4.593667 | 8.643708 |
| 결과 직렬화/전송→ack | 9.059375 | 5.411250 | 11.682250 |

기존 간격에서 약 1초였던 결과 age는 B에서 약 100ms로 낮아지고 A2에서 다시 약 1초로 돌아왔다. 이 대조는 조회 간격이 이번 순차 경로의 지연에 영향을 주었다는 근거다. Kafka 자체를 더 빠르게 만든 실험은 아니다.

DB age는 INSERT부터 SELECT 문장 시각까지로 트랜잭션 시간과 wall clock 영향을 포함한다. batchWait·sendAck는 JVM 단조 시계다. 서로 다른 P95를 더하거나 브라우저 지연에서 빼서 Consumer/네트워크 소요 시간으로 간주하지 않는다.

## 조회 빈도와 DB CPU

| 조건/창 | 관측 길이(초) | 완료 poll | 빈 poll | 완료/초 |
|---|---:|---:|---:|---:|
| A1 유휴 | 60.001 | 60 | 60 | 1.000 |
| B 유휴 | 60.003 | 566 | 566 | 9.433 |
| A2 유휴 | 60.002 | 60 | 60 | 1.000 |
| A1 입찰 | 41.798 | 41 | 1 | 0.981 |
| B 입찰 | 8.587 | 79 | 39 | 9.200 |
| A2 입찰 | 42.748 | 42 | 2 | 0.983 |

모든 창에서 poll 실패·duration 누락은 0개였다. 유휴 발행은 0개, 입찰 창의 총 발행은 각 40개였다. 현재 경로에서 poll 한 번은 미발행 SELECT 시도 한 번을 거치지만, 이 값은 **수집 창에 수신한 완료 호출 수**이지 정확한 DB 전체 SELECT 수가 아니다. 창 경계의 실행 중 호출·비동기 전달 오차와 로그 누락 가능성이 남아 있다. 100ms fixed delay도 정확히 초당 10회를 보장하지 않는다.

| 조건 | 유휴 CPU 표본 | 유휴 중앙값 / 최대 | 입찰 CPU 표본 | 입찰 중앙값 / 최대 |
|---|---:|---:|---:|---:|
| A1 | 242 | 0.210% / 2.06% | 168 | 0.755% / 4.14% |
| B | 240 | 0.985% / 8.30% | 34 | 2.510% / 4.43% |
| A2 | 242 | 0.210% / 3.47% | 170 | 0.760% / 2.15% |

모든 창이 CPU 최소 5개 기준을 충족했다. B의 유휴 중앙값은 A1/A2보다 0.775%p 높았다. 입찰 중앙값은 약 1.75%p 높지만 B의 관측 창이 훨씬 짧아 같은 시간의 지속 부하 비교는 아니다. 이벤트가 없어도 빈 조회가 늘어나는 비용이 있어, 단순히 더 짧을수록 좋다고 결론 내리지 않는다.

CPU는 동일한 `docker stats` 클라이언트의 live 출력이다. 표본은 약 0.25초 간격의 수신값이며 Docker 내부 갱신/반복 값이 포함될 수 있다. 표본 수를 독립적인 측정 횟수로 취급하지 않는다. PostgreSQL 컨테이너의 CPU 비율이지 호스트 전체·SQL별 비용·AWS 비용이 아니다. 변경하지 않은 다른 로컬 서비스·DB 부수 작업·호스트 스케줄링의 영향도 배제하지 못한다.

## 데이터 정합성과 로그 연결

본측정 A1/B/A2 각각 다음을 확인했다.

- 요청·승인 요청·원장·승인 원장·서로 다른 원장 requestId·정산 이벤트 각 20개.
- 최종 현재가 30,000원, `ACTIVE / version 21`, 최종 승자·가격은 최신 승인 이벤트와 일치.
- 이벤트 version 순 가격 역행 0개. 명령 20개·승인 결과 20개의 requestId 집합은 브라우저 표본과 일치.
- 이벤트별 ack 1개·발행 표시 1개, 회차당 매칭 로그 80개. 누락/중복·MISSING/INVALID age 0개. 세 조건 모두 P50/P95/P99를 유효 20개에서 계산.

이는 로컬 순차 60건의 확인이다. 동시 요청·재발행·장애 복구에서도 같은 성질이 유지된다는 추가 증명은 아니다. 시험 데이터와 기존 볼륨은 지우지 않았다.

## 중단 회차와 실행 연결 점검

채택한 회차보다 앞서 두 번 실행이 중단됐다. 실패 결과를 삭제하거나 유리한 표본만 선택하지 않도록 별도 증적에 남겼다.

1. 첫 시도는 A1 워밍업·입찰 20건을 수집했다. 기본 P95는 2,939.36ms로 실패했다. 이후 읽기 전용 `docker stats` 클라이언트가 종료 신호에 응답하지 않아 종료 대기가 초과했고 B/A2를 실행하지 못했다. 전체 A-B-A 비교로 채택하지 않았다. 수집 JSON·브라우저 원본은 그대로 보존했다.
2. 두 번째 시도는 실행자의 API 소유권 확인이 상대 JAR 경로를 허용하지 않아 사전 점검에서 중단됐다. 워밍업/본측정은 시작하지 않았다.

실행 연결을 보완한 뒤 A1부터 전체 순서를 새로 실행했다. CPU 창 종료 후 해당 stats **클라이언트 프로세스만** 강제 종료했다. PostgreSQL이나 다른 컨테이너를 중단/초기화한 것이 아니다. 이 보완은 임시 실행 연결에 한정되며 제품 코드·수집기·임계값을 바꾸지 않았다. 사전 점검/종료 실패를 제품 입찰 실패나 정상 실험으로 바꾸어 세지 않았다.

## 검증과 다음 판단

- 기존 Node 관련 테스트 19개 통과. bootJar 생성/재사용 확인. 이번 문서 작업에서는 백엔드 전체 check나 프런트 컴포넌트 테스트를 재실행하지 않았다.
- 브라우저 원본 요약과 각 창의 poll/CPU 집계를 기존 순수 함수로 다시 계산해 일치 확인했다. 명령/결과 eventId별 로그와 SQL 무결성도 assert했다. nearest-rank 백분위를 유지했다.
- 복원한 실제 listen PID와 실행 인자의 `local / 1000 / INFO`, health HTTP 200을 별도로 확인했다. 복원 기록만 믿고 이전 e2e 프로세스를 정상 local로 간주하지 않았다.

사양의 후보 판정(기본 P95 ≤ 2초, B의 화면·명령 age·결과 age P95가 A1/A2보다 낮음)은 이번 회차에서 충족했다. **100ms를 설정 후보로 검토할 근거는 확보했지만 기본값은 바꾸지 않았다.** 채택은 보고서 검토 후 별도 설정 PR로 진행해야 한다. #19/#18의 나머지 범위도 열린 상태다. 동시 부하·오래된 Outbox 누적·장애/재시도·AWS 성능과 비용은 이번 실험으로 검증하지 않았다. AWS 작업은 없었다.
