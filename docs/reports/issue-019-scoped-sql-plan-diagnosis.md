# 반복된 정산 조회 시간 초과의 읽기 전용 진단

[#302](issue-019-load-browser-convergence.md)와 [#312](issue-019-ingress-full-verification.md)는 모두 본 실행에서 1,000건을 접수했지만 정산 조회가 4초 제한으로 취소됐다. **중복 SQL 조건 제거는 현재 데이터에서 성능 개선 근거가 없었다.** 대신 정산이 진행 중인 상태에 전체 원장 조회를 걸 가능성을 줄이기 위해, 저비용 완결 확인을 앞에 두는 [사양](../specs/issue-019-settlement-snapshot-gate.md)을 제안한다.

## 실패 직전 기록

| 실행 | 마지막 관측 Lag 합계 | 해당 Lag 조회 완료 → 실패 SQL 시작 |
|---|---:|---:|
| #302 | 208 | 5.83초 |
| #312 | 204 | 5.77초 |

두 실행 모두 전체 SQL을 호출하기 전에 새 Lag나 요청 완료 수를 확인하지 않았다. 마지막 Lag 표본은 SQL 시작보다 약 6초 앞서므로 SQL 실행 순간에도 그만큼 남았다고 단정할 수 없다. 당시의 잠금, I/O, 플랜, CPU 경합은 관측하지 않았다.

## 기존 SQL과 중복 조건 제거 후보

각 경매에서 이미 제한된 요청 CTE에 붙은 `r.auction_id=a.auction_id`만 제거했다. 같은 read-only repeatable-read snapshot에서 결과 JSON을 비교했고, 순서 없는 배열만 정렬했다(중복 제거 없음). 기존 4초 statement·5초 호출 상한을 유지했다. 두 라운드에서 측정 순서를 서로 바꿨다. 아래는 PostgreSQL EXPLAIN 실행 시간이며 Docker 호출이나 JSON 결과 전송 시간이 아니다.

| 범위 | 기존 실행(ms) | 후보 실행(ms) | 결과 |
|---|---:|---:|---|
| #312 경매 전체 | 32.42 / 31.62 | 32.66 / 30.98 | 동일, 상세 1,000행 |
| #302 경매 전체 | 32.10 / 31.40 | 32.04 / 30.80 | 동일, 상세 1,000행 |
| #312의 지정 요청 2개 | 15.17 / 14.41 | 14.44 / 15.36 | 동일, 전체 카운터 1,000 및 상세 2행 |

경매 전체의 요청 CTE 추정은 7행에서 1,000행으로 바뀌었고 조인 방식도 달라졌다. 하지만 공유 블록 read는 양쪽 모두 0, hit와 임시 블록은 각 쌍에서 같았고, Outbox 순차 스캔도 남았다. 사후 소표본에서 시간과 관측 비용의 근거 있는 개선은 없었다. 따라서 쿼리나 인덱스를 바꾸지 않는다.

별도로 만료/완료 여부를 판정하지 않고 해당 경매의 요청 전체 수와 최종 상태 수만 세는 후보 계획은 #312에서 0.751ms, #302에서 0.683ms였다. 두 경우 임시 블록 I/O가 없고 원장·Outbox는 읽지 않았다. 이 수치는 부하가 없는 현재 스냅샷에서의 비교이며, 당시 부하 구간의 동시성이나 회복 시간을 재현하지 않는다.

## 사후 상태와 유지 경계

#312의 **사후 조회**에서 요청·원장·결과 각 1,000건 및 50,010,000원/v118의 마지막 승인 도메인 eventId를 확인했다. 이는 실행 때 보존한 A/B 공개 이벤트와 일치하지만, 조회가 취소된 본 실행의 SQL·Lag/DLT·화면 판정을 소급해 통과시키지 않는다. #302와 #306의 기존 판정도 유지한다.

[구조화 증적](evidence/issue-019-scoped-sql-plan-diagnosis.json)은 집계와 계획의 허용 필드만 포함한다. 원문 SQL/로그, 타 사용자 데이터, 환경 값은 포함하지 않았다. 기존 API PID 54954/readiness UP을 유지했으며 새 부하·API 재시작·DB 변경·AWS 작업은 없었다.
