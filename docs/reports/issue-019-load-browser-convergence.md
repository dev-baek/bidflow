# 천 건 부하의 브라우저 관측과 SQL 시간 초과

[#301 승인 사양](../specs/issue-019-load-browser-convergence.md)에 따라 기존 집중 부하 수집기에 공개 WebSocket과 두 화면의 관측을 연결했다. **10건 smoke는 통과했고, 본 실행은 1,000건 접수 뒤 PostgreSQL 조회 시간 초과로 미완료됐다.** 같은 경매의 사후 읽기 전용 조회는 원장 정합성 및 최종 공개 frame의 ID를 확인했지만 본 실행 판정을 바꾸지 않는다.

## 구현과 검증

- 기존 k6 요청 계획·SQL·자원·명령 추적을 재사용했다. 관측자를 켜지 않은 기존 CLI 경로는 그대로다. 새 의존성이나 업무 API 변경은 없다.
- 두 Playwright context에서 앱의 실제 공개 구독을 관측한다. 한 Node 단조 시계로 부하 구간과 frame·화면 확인 시각을 기록하고, 최종 SQL 도메인 eventId·가격·version·마감과 대조한다. 앱의 상세 재조회 경로를 그대로 사용한다.
- 순수 판정 모듈 부재와 observer 미연결에서 RED를 확인한 뒤 최소 구현했다. 역할·ID·가격·시각·중복·상한과 준비/실행 중 소실/정리 실패를 테스트했다. `make verify` Node 125개·Vitest 71개·빌드 및 별도 기존 E2E TypeScript 검사 통과. 새 JavaScript 관측기는 구문 확인과 실제 브라우저로 검증했다.

## 실제 결과

실행 SHA `c4bf0f0064940a237c134ec24e82a63bd33fd2fd`. 2026년 11월 22일 21:04:37~21:05:44 JST, 공유 Mac arm64 16 GiB, Node 24.18.0·Java 21.0.7·k6 0.54.0, local/system Clock/100ms와 loopback Vite preview. 기존 승인대로 새 경매 두 개에서 각각 한 번 실행했고 재시도하지 않았다.

| 지표 | smoke 2 VU × 5 | 본 실행 20 VU × 50 |
|---|---:|---:|
| 완료 iteration/유효 접수 | 10/10 | 1,000/1,000 |
| HTTP P50/P95/P99 (ms) | 67.77 / 107.20 / 107.53 | 16.29 / 93.79 / 248.28 |
| HTTP 오류율 | 0% | 0% |
| 공개 frame A/B | 7/7 | 266/266 |
| 관측 최대 Lag | 0 | 208 |
| 실행 중 원장·화면 판정 | 통과 | 미완료: SQL 시간 초과 |

smoke는 승인 6·거절 4, 최종 510,000원/v7이다. 두 화면 모두 부하 종료 전에 수렴했다. 최종 frame 이후 화면 확인까지 A 5.65ms, B 6.11ms였다. 이는 상세 재조회와 DOM 확인을 포함하며 전송 지연 P95가 아니다.

본 실행에서 두 브라우저가 50,010,000원/v266의 같은 최종 이벤트를 부하 종료 관측 약 8.01초 후에 수신했다. SQL 성공 뒤에만 연결 판정과 화면 시각을 저장하는 구조라 **본 실행의 최종 DOM 확인 시각은 증적에 없다.** WebSocket 수신을 화면 수렴으로 대신하지 않는다. 자원 최종 판정과 DLT 사후 대조에도 도달하지 못했다. 위 HTTP 수치는 접수 구간의 부분 관측이다.

## 실패 원인과 복원

본 실행 첫 `SCOPED_SQL`은 4.224초 뒤 exit 1이었다. 같은 실행 시각 PostgreSQL 로그에 `canceling statement due to statement timeout`이 있고 해당 조회의 제한은 4초다. 이는 5초 프로세스 타임아웃이나 HTTP 실패와 다르다. 당시 SQL이 4초를 넘긴 세부 원인은 미확정이다.

검증 JVM·Vite를 종료하고 기존 1,000ms API를 PID 94652로 복원했다. 기존 jar hash·정확한 인자·listen PID·readiness UP을 대조했다. 기존 데이터·볼륨·Redis key·Kafka offset을 초기화하지 않았다.

복원 후 21:06:08 JST에 해당 본 실행 경매만 같은 제한으로 한 번 읽었다. 231ms 안에 요청·원장·결과 각 1,000건, 승인 265·거절 735, 미처리 0 및 순수 정합성 판정 통과를 관측했다. 최종 도메인 eventId·가격/version도 A/B frame과 일치했다. 사후 조회는 원래 실패 순간의 SQL/DOM/Lag/DLT·자원 판정을 복구하지 않는다.

[구조화 증적](evidence/issue-019-load-browser-convergence.json)에는 최종 frame·집계·판정·복원 정보를 보존했다. 원본 로그/전체 frame은 로컬 보호 경로에만 유지했다. 다음 검증 전에는 조회 시간을 늘리기보다 기존 쿼리 계획을 확인하고, SQL 실패 시에도 부분 DOM 관측을 남기는 조건을 먼저 검토한다. 1,000건 전체 동시 HTTP·요청별 전달 P95·AWS는 검증하지 않았다.

[후속 사양](../specs/issue-019-scoped-sql-reliability.md)에 사후 읽기 전용 쿼리 계획과 부분 DOM 보존 조건을 기록했다. 사후 계획은 본 실행의 실패 판정을 바꾸지 않는다.

## SQL 실패 분류와 부분 화면 보존

#303 승인에 따라 집중 부하의 읽기 전용 snapshot 호출에서 PostgreSQL 쿼리 취소(57014), 로컬 프로세스 시간 초과, 잘못된 JSON 출력, 기타 호출 실패를 고정 코드로 구분했다. 57014만으로는 statement timeout이라고 단정하지 않는다. 원문 오류와 SQL은 증적에서 제외한다.

관측 중 완료된 DOM 확인은 역할·경매·이벤트 ID·가격·단조 시각만 기록한다. SQL 예외 뒤 새 화면 대기를 시작하지 않고, 이미 수집된 frame/DOM을 정리 전에 동결한다. 느린 콜백이나 정리 실패로 기록이 유실되거나 성공으로 바뀌지 않는다. 화면 후보는 SQL의 승인 이벤트와 대조하기 전에는 완전한 수렴 증거가 아니다.

모듈/수집 경로 미구현 상태에서 RED를 확인한 뒤 보완했다. 관련 Node 테스트 51개와 JavaScript 구문 검사를 통과했다. 기존 쿼리는 그대로이며, 4초 statement·5초 프로세스 제한도 유지했다.

2026년 11월 23일 17:40:08 JST에 기존 경매 두 건의 snapshot 호출을 읽기 전용으로 확인했다. 10건 경매의 요청/원장/결과는 각 10건(171ms), 1,000건 경매는 각 1,000건(230ms)이었다. 접수 ID에 연결된 키·입찰자·금액 및 최종 승인 이벤트 ID·가격·version이 기존 증적과 일치했다. 두 경매는 이미 ENDED였고 현재 경매 version은 각각 8과 267, 마지막 입찰 결과 version은 7과 266이다. 이는 활성 부하 판정이나 쿼리 속도 개선 측정이 아니다.

새 부하·브라우저 실행과 API 재시작, AWS 작업은 하지 않았다. #302 본 실행 결과는 미완료로 유지한다.
