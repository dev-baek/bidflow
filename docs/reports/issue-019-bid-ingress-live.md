# 로컬 입찰 접수 계측의 실제 요청 검증 결과

[#309 승인](../specs/issue-019-bid-ingress-live.md)에 따라 새 경매에서 2 VU × 5회 smoke를 한 번 실행했다. **10개 응답을 모두 서버 접수·타이밍 로그와 연결했고, 별도로 기존 smoke 기준도 통과했다.** HTTP P95는 201.38ms였으며, #306의 300ms 초과는 이번 표본에서 관측되지 않았다. 두 실행은 통제된 비교가 아니므로 이전 지연 원인이 해결됐거나 계측 후 성능이 향상됐다고 보지 않는다.

## 실행 및 판정

2026년 11월 23일 18:22:51~18:23:11 JST, 소스 `4cbcb9fb3ecc1e62203dc0cda3f14d6fc2c4570a`의 별도 깨끗한 worktree에서 실행했다. Node 24·Java 21·k6 0.54.0, local/system Clock/100ms/INFO와 loopback Vite를 사용했다. 기본 검증(Java 단위, Node 130개, Vitest 71개, 빌드)과 환경 사전 점검이 통과했다.

| 항목 | 결과 |
|---|---|
| 실제 계측 연결 | `runtime.apiMode=INGRESS_TIMING`. 10개 응답에 고유 UUID 상관 ID 10개. 동일 JVM의 접수 로그 10개·타이밍 로그 10개에 요청 ID로 각각 연결. 누락·중복·파싱 오류 0. `joinBidIngress.complete=true`. |

새 경매의 원래 receipts 10개 전체와 시험 JVM 로그를 다시 대조했다. 두 브라우저 모두 부하 종료 관측 전에 최종가를 표시했으며, 최종 frame부터 DOM 단언까지 A 9.83ms, B 10.17ms였다. 입찰 원장 판정과 화면 판정도 저장된 동일 실행의 SQL·브라우저 증거로 재계산했다.
