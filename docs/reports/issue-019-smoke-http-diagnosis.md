# 입찰 접수 지연의 요청별 대조

[#306 smoke](issue-019-load-browser-revalidation.md)의 HTTP 표본 10개를 서버 접수·정산 로그와 연결했다. **300ms를 넘긴 세 요청 중 두 건은 접수 저장 콜백 진입부터 접수 로그까지 215ms 이상이었고, 나머지 한 건은 약 64ms였다.** 두 느린 요청에서 접수 저장 경계의 긴 구간을 찾았지만, 세 요청의 지연을 같은 원인으로 설명할 수는 없다.

## 대조한 자료

원래 2026년 11월 23일 17:55 JST 실행의 k6 duration, 시험 JVM 로그, 저장된 원장 판정을 사용했다. 같은 경매의 기존 `bid_request` 시각은 18:04:02 JST에 read-only SQL로 한 번 읽었다(4초 statement/5초 프로세스 상한). 새 요청·설정 변경은 없었다.

10개 응답 requestId 각각의 같은 auctionId에서 `bid.request.received`와 `bid.settled`가 정확히 하나씩 있었다. 두 로그의 correlationId가 맞았고 정산 판정 5승인·5거절이 저장 원장 및 현재 요청 상태와 일치했다. 정산 입력은 모두 같은 partition 2의 서로 다른 offset이었다. 이 연결은 접수와 이후 비동기 정산을 나타내며, 요청 진입/응답 완료나 DB 커밋 시각을 복원한 것이 아니다.

## 느린 표본과 나머지 표본

| 표본 | HTTP duration | 저장 콜백 진입 → 접수 로그 | 접수 로그 → 정산 로그 |
|---|---:|---:|---:|
| index 2 | 313.31ms | 231.91ms | 591.14ms |
| index 3 | 305.23ms | 215.19ms | 592.86ms |
| index 4 | 307.07ms | 63.57ms | 215.57ms |
| 나머지 7개 (범위) | 16.70–200.28ms | 7.45–48.01ms | 208.27–988.45ms |

- `JdbcBidRequestRepository.saveIfAbsent`에서 `requested_at`은 트랜잭션 콜백 진입 뒤 첫 INSERT 전에 앱 시계로 정해진다. `bid.request.received`는 `service.receive`가 반환된 뒤 응답을 반환하기 전에 기록한다. 이 두 점의 차이는 INSERT 두 개와 트랜잭션 반환 및 로그 기록 전 시간을 포함한다. 멱등 조회, 콜백 진입 전 연결/트랜잭션 준비와 응답 직렬화·전송은 포함하지 않는다. 순수 SQL 실행 시간 또는 개별 커밋 시간은 아니다.
- `bid.settled`는 Kafka 소비자가 별도 경로에서 원장 저장 호출이 성공한 뒤 기록한다. HTTP가 이 결과를 기다리지 않으며, 약 61ms에 접수된 첫 두 요청의 정산 로그 간격은 각각 약 988ms와 964ms였다. 소비자와 HTTP 경로의 간접 자원 경합 여부는 현재 기록만으로 판정할 수 없다.
- k6 전체 대기 구간 P95 309.72ms는 클라이언트에서 첫 응답 바이트를 기다린 분포다. 원래 수집에는 요청별 구간 시간이나 서버 진입·응답 완료 시각이 없다. k6 duration에서 서버 구간 또는 다른 백분위를 빼서 남은 시간을 계산하지 않는다.

결론은 **저장 콜백 이후 구간이 일부 느린 요청에서 길었다**는 데까지다. 커넥션, 쿼리, 커밋, 서버 스케줄링 중 무엇이 원인인지는 미확정이다. 다음 단계는 [접수 구간 계측 사양](../specs/issue-019-bid-ingress-timing.md)의 검토다. [구조화 증적](evidence/issue-019-smoke-http-diagnosis.json)에는 원문 로그나 상관 ID를 복사하지 않고 상대 시각과 표본만 남겼다. 기존 API PID 23439와 readiness를 유지했다. 부하 재시도·AWS 작업은 하지 않았고 #306의 성능 미달과 #302의 SQL 실패 판정을 유지한다.
