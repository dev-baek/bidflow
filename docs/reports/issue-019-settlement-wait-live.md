# 정산 SQL 대기 관측 실제 부하 결과

**누적 1,000건의 접수와 요청별 계측은 확인했고, 같은 정산 명령의 대기 표본 41개를 확보했다. 전체 검증은 기존과 같이 서버의 4초 정산 SQL 취소로 미통과했다.** 활성 표본 39개 중 1개에서 I/O 대기가 관측됐다. 나머지 38개에서 대기가 표시되지 않았으며, 이 표본으로 취소의 원인이나 CPU 사용 시간을 확정할 수 없다.

## 실행과 단계 판정

[#323 승인 계획](../specs/issue-019-settlement-wait-live.md)에 따라 2026년 11월 25일 10:39:49~10:41:08 JST, 소스 `ea155e2b6833a6182876365a7b44f35b96a931cf`의 별도 worktree에서 실행했다. 사전에 `make verify`(Java 단위 테스트, Node 144개, Vitest 71개, 빌드)를 통과했다. 스모크와 본 실행에는 별도 경매와 출력 경로를 사용했다. local/system Clock/100ms/INFO, 요청 계측과 `--settlement-waits`를 켠 loopback 환경이었다.

| 항목 | 스모크 2 VU × 5회 | 본 실행 20 VU × 50회 |
|---|---|---|
| HTTP | 10/10 접수, 오류 0%, P50/P95/P99 23.63/87.53/87.55ms | 1,000/1,000 접수, 오류 0%, 18.47/165.66/939.74ms |
| 접수 계측 | 10/10 연결 | 1,000/1,000 연결 |
| 정산 SQL | 1회, 290.17ms, 요청·원장·결과 각 10개(승인 10) | 1회, 4,163.73ms, 서버 취소 |
| A/B 화면 | 510,000원/v11과 최종 승인 일치 | 두 브라우저의 50,010,000원/v96 기록은 남았으나 SQL 대조 미완료 |
| 대기 관측 | 같은 명령의 표본 3개(활성 1), 오류 0, 정리 확인 | 같은 명령의 표본 41개(활성 39), 오류 0, 정리 확인 |
| 후속 확인 | Lag [0, 0, 0], DLT 불변, 최종 자원 확인 | SQL 실패로 후속 Lag/DLT·최종 자원 판정 미실행 |
| 실행기 | exit 0, `valid=true`, `browserObservationValid=true`, `fullVerified=false` | k6 exit 0, 실행기 exit 1, `valid=false`, `fullVerified=false` |

새 스모크가 기존 판정과 대기 관측 경로를 모두 통과한 뒤에만 본 실행을 시작했다. 본 실행의 HTTP 수치는 기존 P95 < 300ms·오류율 < 1%를 충족했으나, SQL 실패로 실행기의 종합 판정은 완료되지 않았다. 1,000건은 20 VU의 누적 제출이다.

## 정산 호출과 대기 표본

본 실행에서 부하 종료 **+8.991초**에 Kafka 세 파티션의 새 Lag 0, **+9.186초**에 해당 경매의 전체/완료 1,000/1,000을 확인했다. **+9.260초**에 정산 명령 #38을 한 번 시작했다. 해당 명령은 로컬 5초 제한 전에 `SQL_QUERY_CANCELED` 및 `STATEMENT_TIMEOUT`을 남겼다. 같은 시각의 PostgreSQL 로그(10:40:59.542 JST)에서도 statement timeout을 확인했다.

| 본 실행 표본 분류 | 개수 | 의미 |
|---|---:|---|
| `IO` | 1 | 정산 명령 시작 후 약 2.34초의 요청·응답 구간에서 대상 SELECT의 I/O 대기를 관측했다. |
| `NO_WAIT_OBSERVED` | 38 | 대상 SELECT가 활성 상태였고 해당 표본에 표시된 대기가 없었다. |
| `NO_TARGET` | 2 | 표본에 일치하는 세션이 없었다. 활성 표본으로 세지 않았다. |

표본 요청·응답 시각은 모두 명령 #38의 구간 안에 있었으며, 시작 간격은 100ms 이상, 수신 간 최대 간격은 103.24ms였다. 잠금 또는 클라이언트 대기 표본이 없었다는 사실만으로 틈 사이의 대기를 배제할 수 없다. 1개 I/O 표본을 대기 시간으로 환산하지 않았고, [#316](issue-019-settlement-gate-live.md)을 포함한 이전 실패의 원인도 소급 확정하지 않는다.

## 복원 및 남은 검증

관측기·k6·Chromium·Vite·검증 JVM을 정리했고, 기존 1,000ms API의 jar·인자·listen·readiness UP을 확인했다. 로컬 컨테이너 5개의 ID·healthy 상태는 그대로였다. [구조화 증적](evidence/issue-019-settlement-wait-live.json)은 집계, 상대 시각, 판정과 정리만 담는다. 원본과 요청별 계측은 보호된 저장소 외부 경로에 보관했다.

재시도, 사후 DB 조회, 제한 완화, 장애 주입, AWS 작업은 하지 않았다. 계정 없이 진행할 수 있는 인증·배포 준비는 이번 정산 이슈와 분리한다. #19의 같은 실행 정산 원장·화면 대조는 여전히 미완료다.
