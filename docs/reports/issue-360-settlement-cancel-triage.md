# [Issue #360] 정산 검증 SQL 4초 취소 진단

- 작업: [#360](https://github.com/dev-baek/bidflow/issues/360), 상위 [#19 부하·장애 검증](https://github.com/dev-baek/bidflow/issues/19)
- 근거: [#324 실제 관측](issue-019-settlement-wait-live.md)과 [증적](evidence/issue-019-settlement-wait-live.json), [#332 격리 비교](issue-019-settlement-sql-phases.md)와 [증적](evidence/issue-019-settlement-sql-phases.json)
- 판정: **서버의 statement timeout은 확인했다. 왜 4초를 넘었는지는 미확정이다.** 이번에는 기존 기록과 코드를 점검했고, 조회나 부하를 재실행하지 않았다.

## S. 사용자 결과와 검증 판정

실제 실행은 **20 VU × 50회에서 누적 1,000건**을 제출한 것이며, 1,000개 동시 HTTP 요청이 아니다. #324에서 1,000/1,000 접수, HTTP P95 165.66ms, 오류율 0%였다. 부하 종료 후 새 Kafka Lag 표본에서 3개 파티션이 0이었고 해당 경매의 요청·완료 각 1,000건을 확인했다. 이 저비용 완료 확인은 요청 상태를 확인한 것이지, DB와 주변 서비스가 모두 유휴라거나 원장·결과 이벤트·화면이 일치한다는 증거가 아니다.

정산 검증 SELECT의 실패로 그 실행의 원장·A/B 브라우저 대조와 후속 Lag/DLT를 완료하지 못했다. 브라우저 부분 증적과 HTTP 기준 충족은 유지하되 전체는 `fullVerified=false`다. 취소된 SQL은 입찰 API의 요청 처리 쿼리가 아니라 별도 **검증기**의 집계 SELECT다.

## D. 같은 SELECT, 다른 관측 조건

| 비교 | #324 로컬 실제 실행 | #332 격리 합성 비교 |
|---|---|---|
| 대상과 주변 작업 | 기존 Compose PostgreSQL의 영구 볼륨, 입찰·Kafka·브라우저 검증과 같은 실행 창. 당시 테이블 크기·플랜·DB/호스트 자원 계측 없음 | PostgreSQL 17.5의 임시 파일시스템, 공개 포트 없음. 기존 마이그레이션과 고정 fixture 적용 후 `VACUUM (ANALYZE)`. 배경 이벤트 2,000/100,000개, 앱 부하 없음 |
| 호출 | `docker exec`의 태그 있는 psql, 개별 `-c`로 설정·SELECT·COMMIT. 별도 psql이 대상 세션의 대기를 약 100ms 간격으로 샘플링 | `docker exec -i`로 표준 입력에 같은 경매 범위 SELECT를 전달. 일반 호출과 `EXPLAIN SERIALIZE NONE/TEXT`를 각각 3회씩 순환. 대기 샘플러 없이 실행 |
| 결과 | 명령 #38은 호출 후 4,163.729ms에 실패. `57014`와 서버 로그가 `STATEMENT_TIMEOUT`을 확인. 로컬 호출 제한은 5,000ms | 준비 2회와 측정 18개 통과. 일반 psql 최대 435.749ms. `SERIALIZE TEXT`의 텍스트 변환 3.387–5.592ms. 두 규모의 일반 결과 해시 동일 |

#324에서 같은 명령 구간의 표본은 41개다. 활성 39개 중 I/O 1개(명령 시작 후 2,339.156–2,340.937ms 사이의 관측 요청/응답), 표시된 대기 없음 38개, 대상 없음 2개였다. 이 구간은 I/O **지속시간**이 아니다. 활성 상태와 대기 표시는 독립적이며 표본 사이 최대 간격이 103.238ms였다. 잠금·클라이언트 대기 표본이 없었어도 발생을 배제할 수 없고, 대기 표시가 없었던 시간을 CPU 실행 시간으로 환산할 수 없다. [PostgreSQL 대기 관측](https://www.postgresql.org/docs/17/monitoring-stats.html)

#332에서 무관 이벤트가 많은 쪽은 Outbox 공유 블록 hit가 증가했지만, 두 규모 모두 Outbox 공유 블록 read는 0이었다. 이는 당시 계획의 버퍼 접근이고 #324의 I/O 원인이나 시간은 알려주지 않는다. `EXPLAIN SERIALIZE`는 결과를 클라이언트에 전송하지 않으므로 그 시간과 일반 호출 경과의 차이를 순수 전송 지연으로 해석하지 않는다. [EXPLAIN 계측 범위](https://www.postgresql.org/docs/17/sql-explain.html)

**좁혀진 범위:** 온전한 합성 결과의 크기를 처리하는 것만으로 취소가 재현되지는 않았다. 실제 실행의 데이터 분포·플랜·캐시와 저장 경로, 쿼리 수행 중 자원 경합, 관측 호출 방식의 영향은 아직 분리하지 못했다. [#316](issue-019-settlement-gate-live.md)도 같은 서버 제한으로 실패했고, [#320 인덱스 비교](issue-019-settlement-outbox-comparison.md)는 채택 기준에 미달했다. 스키마·인덱스·제한과 이전 판정을 그대로 둔다.

## B. 다음 재현 계획 — 실행은 별도 승인

1. **호출과 관측의 영향부터 분리한다.** 네트워크·공개 포트가 없는 전용 PostgreSQL 17.5에 #332의 합성 fixture와 동일 마이그레이션을 적용한다. 같은 DB·사용자·SELECT·출력 계약을 고정하고, 표준 입력과 태그가 붙은 분리 `-c`를 각 3회 순서를 바꿔 대조한다. 이때 관측기는 끈다. 다음에 태그 호출을 고정해 관측기 없음/있음만 같은 방식으로 비교한다. 현재 live 실행기는 기존 컨테이너 이름을 고정하므로 그대로 실행하지 않는다. 구현한다면 실험에서 소유권을 확인한 임시 컨테이너만 받도록 하고, 이름·image digest·mount를 검증한다.
2. **플랜과 저장 경로를 분리한다.** 호출 방식·관측 조건을 고정한 뒤 배경 이벤트 2,000/100,000의 #332 결과를 기준선으로 삼는다. 저장 경로 영향은 새 격리 컨테이너의 tmpfs와 실험 전용 새 Docker 볼륨만 비교한다. 같은 행·스키마·통계 준비 방식과 실행 순서를 사용하고 기존 Compose 볼륨은 마운트하지 않는다. 열화가 있는 조건에서만 같은 SELECT의 `EXPLAIN (ANALYZE, BUFFERS, SERIALIZE NONE/TEXT, FORMAT JSON)`로 계획·블록·변환을 대조한다. 필요 시 쿼리 세션에서만 I/O 타이밍을 별도로 허용하고 계측 오버헤드를 밝힌다. 취소로 계획 출력이 없으면 **미수집**으로 기록한다.
3. **대기 증거를 같은 명령에 묶는다.** 재현 중 서버 취소 사유, 호출 시작·종료, 태그와 backend 식별자, 서로 다른 타입의 대기 표본과 표본 누락을 연결한다. 잠금이 반복 포착되면 동일 시간대에 차단자 유무를 읽기 전용으로 확인하고, I/O 표본은 성공한 비교 실행의 블록·타이밍과 함께 본다. DB·Docker VM의 CPU/I/O 지표를 확보하더라도 컨테이너·클러스터 합계를 해당 쿼리 시간으로 배분하지 않는다. 원본 SQL·실제 데이터·PID·서버 로그는 게시하지 않는다.

## T. 중단·완료 기준

- 진단 쿼리는 읽기 전용, 서버 4초·호출 5초를 유지한다. 임시 데이터 준비 실패, 첫 결과 계약 실패, 시간 초과 또는 대상 불일치 시 그 조건을 중단하고 자동 재시도하지 않는다. 결과는 명령 경과, 안전한 실패 코드와 결과 동등성으로 구분한다. `57014`만으로는 statement timeout과 수동 취소를 구별하지 않는다. [PostgreSQL 제한 설정](https://www.postgresql.org/docs/17/runtime-config-client.html)
- 같은 조건에서 재현하고 다른 단일 조건과의 차이 및 같은 명령의 대기/계측이 뒷받침할 때만 원인 후보의 우선순위를 높인다. 재현되지 않거나 관측이 부족하면 **미확정**을 유지한다. 격리 재현은 #19의 실제 원장·화면 대조를 대체하지 않는다.
- 이번 #360의 산출물은 증적 비교와 재현 계획이다. 기존 DB 재조회·인덱스/설정 변경·새 입찰 부하·AWS 접근은 하지 않았다. 실제 부하 재검증이 필요해지면 범위와 횟수부터 승인받는다.
